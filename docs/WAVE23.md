## Ф1. Предупреждение на «Зафиксировать» / «Снять фиксацию»

**СДЕЛАНО И ПРИНЯТО 2026-10-15** (JOURNAL 2026-10-15, «Окно фиксации»). Попутно — все
браузерные `confirm()`/`alert()` переведены на фирменное окно (`ask()`/`tell()`).
Последняя строка расфиксации — вариант Ивана: «строки и шапку снова можно будет
редактировать — кнопкой «Редактировать»». Решения Ивана: своё
модальное окно (не `confirm()`); последствия **живыми числами** сразу (вариант «Б»);
строку «строки и шапка станут только для чтения» оставить последней — «ломать не
строить, удалим потом легко».

**Что:** каждое переключение фиксации открывает всплывающее окно: что именно произойдёт
(форма станет read-only, документ начнёт/перестанет считаться в балансе и т. п.) и
подтверждение.

**Зачем:** **осознанная шероховатость.** Фиксация — самое весомое действие формы, а сейчас
это такой же клик, как любой другой. Шаг должен быть ощутимым и заметным.

**Подумать при старте:** текст последствий разный по видам (изделие, заказ, ордера,
закупка, проект-архив). Это смысл, значит, он приходит из движка, а вью только рисует
окно (шов движок ↔ вью). Окно модальное: здесь, в отличие от гигиены текста, нужно именно
остановить.

## Ф3. Мобильная (в режиме «как десктоп»): «Потребность» не прокручивается вправо до конца

**Что:** на телефоне с включённой десктопной версией вкладку «Потребность» нельзя
домотать до правого края.

**СДЕЛАНО 2026-10-15, ждёт проверки на телефоне (после деплоя).** Причина: сетка
«Потребности» требует ≥773px, в режиме «как десктоп» (~980px) рабочей области остаётся
~650px, а `.fs-body { overflow: hidden }` молча срезал лишнее. Правка — две строки CSS:
`.fs-list { overflow-x: auto }` (прокручивается тело таба, табы на месте) и
`.pgrid { min-width: min-content }` (строка не уже своих колонок — разделитель не
обрывается). Замер headless-Chrome: на 980px прокрутка до правого края, на 1600px
прокрутки нет, как раньше.

**Приоритет:** не болит, но будет приятно, если правится легко. Скриншоты есть у Ивана —
приложить при старте фазы. Мерить headless-Chrome с мобильным вьюпортом
([[css-measure-recipe]]), а не считать по CSS.

**Подумать при старте (решения нет):** как считать системы (это прибор или контейнер?),

## Ф5. Глиф компонента: библиотечный ≠ ручной

**СДЕЛАНО И ПРИНЯТО 2026-10-15.** Модель Ивана: библиотечный — стрелки, без
фиксации (защищает библиотека); ручной — живёт как изделие: «Зафиксировать» с окном
последствий, глиф-замок везде; пришёл из библиотеки — синк метит `synced`, снимает замок,
глиф становится стрелками. Правка — одна точка `ItemGlyph` + кнопка фиксации в форме +
человеческий отказ движка для библиотечного. Дополнение Ивана: **цена зафиксированного
компонента правится**, синхронно с библиотечным («Редактировать» у зафиксированного
открывает только «Оценку»; изделие заперто целиком — его цена роллап по составу).

**Что:** в списке «Компоненты» развести глифы. **Библиотечный** — зелёные стрелки синка,
**ручной** — замок, оранжевый или зелёный, как у изделий. Ручной уже сейчас отличается:
у него правятся поля, то есть по сути у него есть своя ось фиксации.

**Подумать при старте (решения нет):** сценарии. Сейчас у компонента замок из UI
недостижим (`synced ⟹ not locked`, фиксация только у «Изделий»), а канон
UI_GUIDE §7 говорит «ровно один глиф по режиму». Ручной компонент получает фиксацию? Что
она гейтит? Как это сходится с «глиф перетекает с сущностью во все списки» (BOM,
потребность, заказ)? Что происходит, когда ручной компонент потом приходит из
библиотеки (`mark`)?
