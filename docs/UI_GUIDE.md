# Руководство по интерфейсу — Plume

**Единственный источник правды по интерфейсу.** Однозначная спецификация: и «почему»
(§0), и «что именно» (§1–13). Составлено на интервью 2026-07-04, принято каноном
**2026-07-30** (аудит-1, Б4) — статус «черновик на вычитке» снят: документ описывает
не план, а действующий продукт. [UI_PRINCIPLES.md](UI_PRINCIPLES.md) с этого дня —
**архив**: живые куски перенесены сюда (§0 и §9), остальное отменено жизнью.

Открытых мест (`[ОТКРЫТО]`) не осталось — последнее (§9 «Действия») закрыто решением
задним числом там же.

## 0. Северные звёзды, анти-паттерны и сквозные принципы

Перенесено из UI_PRINCIPLES 2026-07-30 без изменения смысла — это те четыре куска,
которые пережили всю разработку.

### 0.1. Северные звёзды

- **VS Code** — лаконичность, плотность информации, клавиатура, боковые «лупы»
  (Explorer / Search / Git — разные представления одного репозитория).
- **TortoiseGit** — внешне «из 90-х», но непобедим по эргономике: **много информации,
  очень дозированный цвет, богатые (вложенные) контекстные меню**.

Общий вектор обоих: **профессиональный инструмент, а не «школьный сайт»** — мощь в
меню и клавишах, а не в крупных ярких кнопках. Целимся в инвариант (плотность +
дозированный цвет + мощь в меню/клавишах), не в моду.

### 0.2. Анти-паттерны (что убило прошлый UI — не повторять)

- ❌ Отдельные виды «просмотр» и «редактирование» одной формы.
- ❌ Кнопка «редактировать»/«удалить» на **каждой строке** таблицы.
- ❌ Шапка формы, которая уезжает влево или скрывается при редактировании.
- ❌ Бедная форма (2–3 поля) одинокой коробкой по центру пустого экрана.
- ❌ Огромные яркие bootstrap-кнопки; всё крупное давит и съедает место под данные.
- ❌ Поиск/контролы во треть экрана. Крупное = враг.

### 0.3. Прямое редактирование + автосейв

Объект всегда показан в одном виде, всё правится **на месте** (inline); режима
«редактирование» нет. Сохранение — **чистый автосейв** (`PATCH` по полю), большой
кнопки «Сохранить» нет. Это совпадает с мутабельной ДНК модели: всё — живой черновик,
пока не зафиксировано.

Индикатора сохранения **нет** (снят в Ф9, волна 19): при автосейве «сохранено» всегда,
различать нечего — видна только строка `ошибка: …`, когда мутация отклонена (§4).
Read-only — не отдельная страница, а стиль полей под замком/фиксацией (§5).

### 0.4. Цвет = только смысл, дозированно

Цвет тратим **исключительно на смысл** (как git-decorations в VS Code), приглушённый,
не bootstrap-кислота. Статус показываем **значком + цветом текста/тонкой полосой
слева**, а не заливкой фона и не «надувной плашкой» — чтобы плотный грид не рябил.
Значения цветов — по теме (§10), смысл — от движка ([[engine-view-seam]]).

Сквозной словарь статусов (единый везде):

| Знак | Токен | Смысл |
|------|-------|-------|
| `●`  | `--st-wip`   | черновик / в работе / заказано, ждём |
| `▲`  | `--st-order` | дефицит / чего-то не хватает / нужно купить |
| `✓`  | `--st-ok`    | покрыто / готово / лот есть |
| `🔒` | `--st-lock`  | **зафиксировано** (документ проведён, справочник заморожен) — read-only |
| `○`  | `--st-info`  | информационный / нейтральный статус |

`○` в живом интерфейсе почти не встречается — держим в словаре как резерв нейтрального
статуса, а не как обязательный к употреблению знак.

### 0.5. Консистентность: одинаковое делается одинаково

Два действующих стандарта (бывш. Правила 2 и 3 UI_PRINCIPLES; таблицы конформанса к ним
закрыты волной 14 и остались в архиве — сами требования живы).

**Правка полей.** Одинаковое поле в разных формах правится **одинаково** — тем же
контролом, той же логикой замка, тем же guard'ом и теми же текстами ошибок. Разъезд
(«в Изделии артикул правится, в Проекте код — нет») — скрытый долг и путаница.
*Дисциплина, обязательная при любой правке формы:* предлагая или реализуя правку одной
формы, **сразу проверяй применимость ко всем остальным** — опора на соседние `update_*`
в [engine.py](../backend/plume/engine.py). Отставшая форма — это и есть работа, а не
повод завести исключение. Эталон — правка `code`: `.strip()` → пустой →
`ValidationError` → проверка коллизии → «‹Сущность› с кодом X уже есть». `code` не PK,
FK ссылаются по id, поэтому переименование безопасно для связей и истории.

**Удаление.** **Любой** объект должно быть можно удалить **из интерфейса** (не только
из админки), единым паттерном: 🗑 в колонке контролов формы под тем же замком, что
правка → подтверждение при необратимом → friendly-guard движка. Удаление не разрушает
чужую правду: где домен говорит «нельзя» (склад с движениями, зафиксированный документ,
непустой проект), кнопка **всё равно есть** — и объясняет отказ, а не отдаёт 500.
Проект вместо удаления имеет **закрытие** — осознанное исключение, не забытый контрол.

## 1. Словарь частей интерфейса

Русские функциональные имена. Ими пишем инструкции и разговариваем.

| Имя | Что это |
|-----|---------|
| **Панель режимов** | узкая колонка иконок слева; каждая иконка — режим (лупа на данные) |
| **Список режима** | средняя колонка: перечень объектов выбранного режима |
| **Рабочее поле** | центральная зона; в ней открывается форма выбранного объекта |
| **Форма** | экран объекта в рабочем поле: заголовок + шапка-свойства + строки + окружение («форма поставки», «форма изделия») |
| **Заголовок формы** | первая строка формы: **`code`** (первичная идентичность, см. ниже) + мета-строка + замок шапки |
| **Идентичность `code`/`description`** | у каждой сущности пара: **`code`** — короткий уникальный жаргон (в H1 заголовка формы, в списках), **`description`** — развёрнутое имя (в `.props`, не в H1). Правило Ивана 2026-07-24: длинный `description` в заголовке «забирает опору»; заголовок = `code`. Плохой/непонятный код чини сразу. У сущностей без кода (документы) — мягкий фолбэк `code \|\| «УПД №»/«#id»`. Уникальность кода стережётся мягко (дружелюбный отказ, не 500). |
| **Шапка** | панель свойств объекта (пары «подпись: значение») под заголовком |
| **Окружение** | read-only-проекции линзы вокруг объекта (where-used, остатки, дефицит) |
| **Призрачная строка / призрачный пункт** | пустая строка таблицы, появляющаяся сама; пункт «＋ Новая …» первым в списке режима |
| **Замок формы** | бесплатный переключатель редактирования всей формы — шапки и строк (см. §5) |
| **Фиксация** | документное состояние (posted/closed): документ **зафиксирован** — факты учтены движком, форма read-only; обратная операция — «снять фиксацию» (см. §5) |
| **Глифы статусов** | сквозной словарь ● ▲ ✓ 🔒 ○ (см. §0.4) |

Упразднено: слово **«кокпит»** (было размыто) — говорим «форма ‹объекта›». **С
2026-07-26 это правило действует и в коде:** `cockpit` → `form` во всех именах
(`purchase_cockpit` → `purchase_form`, тип `PurchaseCockpit` → `PurchaseForm`,
`useOrderCockpit` → `useOrderForm`). Слово одно на всех слоях — русский интерфейс,
английская модель, движок, типы. `view` в этой роли **не используем**: занято
`views.py` (HTTP-слой) и `*View.tsx` (компоненты). Проекции движка, названные по
UI-контейнеру, при этом чиним по смыслу: ключ `cockpit_status` стал `worst_status`.
**Слово `order` в коде значит РОВНО ОДНО — «Ордер» (`StockDocument`)** (принято
2026-07-26). Оно успело разъехаться: `OrderForm`/`OrderKind`/`orderEntries` звали
ордер, а `addToOrder` клал позицию в **Заказ** (`Purchase`) — две противоположные
роли одного слова. Заказ теперь везде `purchase` (`addToOrder` → `addToPurchase`,
`add_to_project_order` → `add_to_project_purchase`, маршрут `projects/<pk>/order/` →
`add-to-purchase/`). Не трогаем только `to_order`/`on_order` — это ось покрытия
(«надо заказать»/«в заказе»), а не имя сущности. **`order.xlsx` больше не существует:**
маршрут стал `procurements/<pk>/xlsx/`, а **имя скачиваемого файла = `code` закупки**
(«Нева ДЗЗ 1.xlsx»); кнопка в шапке — просто «Скачать». Ярлык сущности уезжает наружу
вместе с файлом, безликого `order-12.xlsx` в переписке с контрагентом больше нет.

Также упразднено:
**строка состояния** внизу — удаляется совсем (автосейв-индикатор переехал в
заголовок формы; счётчики сущностей никто не читал).

## 2. Режимы и иконки

Иконки панели режимов — **Codicons** (родной набор VS Code, MIT, самохостим SVG
как шрифты в `public/`). Монохром: активный режим — белый + полоса слева,
остальные — серые. Эмодзи с панели уходят; **глифы статусов в строках остаются
как есть** (там цвет несёт смысл).

Порядок панели — **поток жизненного цикла изделия**, не история волн: планирование
(закупки) → исполнение (заказы) → приёмка (поставки) → сборка → выбытие/сверка.

| Режим | Codicon | Смысл |
|-------|---------|-------|
| Проекты | `project` | дефицит, панель проекта |
| Изделия | `circuit-board` | справочник, остатки, состав (BOM) |
| **Закупки** | `table` | командный свод, xlsx-бланк (было «Закупки-план») |
| Заказы | `checklist` | обязательства поставщику |
| **Поставки** | `inbox` | УПД, рождение лотов |
| Комплектации | `tools` | сборка, списание под прибор |
| Передачи | `export` | отгрузка заказчику |
| Требования | `arrow-swap` | отпочкование, постановка на баланс |
| Списания | `trash` | выбытие, серый путь |
| Инвентаризации | `search` | найденные партии |
| Выход | `sign-out` | внизу панели |

**Переименование: Receipt = «Поставка»** (появление товаров с накладной), режим
«Поставки». Заменить везде: панель, формы, тексты. Глоссарий README («Приход /
УПД») обновить при ближайшей правке README — предложить отдельно.

Остальные имена режимов — без изменений.

> **Актуальный набор режимов и глифов живёт в `MODES` (`frontend/src/App.tsx`)** —
> таблица выше фиксирует спецификацию чистового прохода, а не сегодняшнее состояние:
> после неё режимы схлопнулись в «Ордера» (волна 13, Ф1b), справочник разошёлся на
> «Изделия»/«Компоненты» (волна 17, там же сменились иконки), а волна 20 добавила
> **«Контрагенты»** (`call-outgoing`) — поставщики и заказчики со своей формой.

## 3. Типографика

Два шрифта, оба самохостятся (OFL):

- **JetBrains Mono** (400/500) — всё **идентифицируемое и счётное**: коды,
  номера документов, количества, деньги, даты, бейджи, мета-строки, **строки
  списков режима** (mono выравнивает похожие названия в колонку).
  Числа — всегда `tabular-nums`, выравнивание вправо.
- **Inter** (400/500) — всё **литературное**: названия изделий и проектов,
  описания, комментарии, подписи полей, кнопки. Заменяет Golos Text
  (файлы Golos удалить вместе с заменой).

**Правило границы:** в одной строке не смешивать mono и текстовый шрифт одного
размера и веса — блоки разводятся размером, весом, цветом или строками. Главный
пример — заголовок формы (§4).

**Деньги — единым форматом везде** (принято 2026-07-26): разряды разделены пробелом,
копейки показываем всегда, знак рубля через пробел — `1 200 300,00 ₽`. Один хелпер
(`money()` в `status.tsx`) на бюджет проекта, суммы документов, оценку изделия. Раньше
он округлял до рубля («копейки в бюджете не важны») — правило снято: деньги выглядят
деньгами.

**Число впереди подписи** там, где строка читается фразой (мета формы, §13.6):
«17 компонентов», не «компонентов 17». Русское склонение обязательно — хелпер
`count(n, 'файл', 'файла', 'файлов')`.

## 4. Заголовок формы (единый для всех форм)

Вариант «название первое»:

```
ООО «Электроконтакт»                    ✓ сохранено  [🔓]
УПД 141 · 02.06.2026 · P-001
```

- 1-я строка: **литературное название** объекта — Inter 500, крупно, белым.
  Справа вверху: **колонка контролов** (§5, Ф9) — режим формы, «Зафиксировать»,
  корзина, каждый как «подпись + Codicon».
- 2-я строка: **мета-строка** — JetBrains Mono, мелко, приглушённо:
  глиф статуса + код/номер · дата · проект (набор зависит от типа объекта,
  разделитель `·`).
- **Индикатора сохранения нет** (снят в Ф9, см. §5): при автосейве «сохранено»
  всегда, различать нечего. Единственное, что может появиться под шапкой, —
  строка `ошибка: …` (красная), когда мутация отклонена.

## 5. Замок формы и фиксация документа

Два разных механизма в **одном слоте** справа вверху заголовка. Различаются
видом: **контур = вид, заливка = фиксация**. Мокап трёх состояний — артефакт
«Два замка» (интервью 2026-07-05).

**Замок формы** — интерфейсный, бесплатный, личный (нигде не хранится,
данных не трогает):

- **Закрыт** (по умолчанию у существующих объектов): контурный 🔒, **вся форма —
  чистый текст без единого поля ввода**: шапка, строки, всё. Эта чистота —
  ценность сама по себе; закрытый вид — основной вид формы.
- **Открыт**: контурный 🔓 — редактируется всё редактируемое: поля шапки и
  строк — инпуты, призрачная строка, автосейв. Переключение мгновенное, в обе
  стороны, без подтверждений; ничего не перестраивается и не уезжает.
- У **черновиков** (только что созданных) замок открыт сразу.

**Уточнено 2026-07-20 (волна 19, Ф9):**

- **Прежние индикаторы убираются:** «✓ сохранено» (зелёная) и «● редактируется»
  (оранжевая). «Сохранено» было неправдой — при автосейве сохранено **всегда**,
  индикатор не различал ничего. Цвет в Plume значит смысл (дефицит, статус), режим
  формы на него не претендует. Слово «Сохранить» не употреблять нигде: операции
  сохранения не существует.

- **Контролы шапки — колонка справа, иконка + подпись слева от неё.** Иконки
  выровнены по правому краю в вертикальную колонку; подписи разной длины прижаты
  вправо и заканчиваются у иконок. Codicons (§2): `edit`, `eye`, `lock`, `unlock`,
  `trash`. Действий ровно три — по правилу §9 (≤3) кнопки на месте, меню не нужно.

- **Правило глифа: и подпись, и иконка говорят, КУДА попадёшь** (назначение, не
  текущее состояние). Состояние читается самой формой — по §5 запертая форма это
  «чистый текст без единого поля ввода», и эта чистота названа ценностью; дублировать
  её иконкой незачем. А последствие клика больше нигде не написано — пусть глиф
  усиливает глагол, а не спорит с ним.

  ```
  черновик, просмотр        Редактировать   ✏️     ← верх-право; корзины нет
                            Зафиксировать   🔒

  черновик, правка               Просмотр   👁     ← верх-право шапки
                            Зафиксировать   🔒
                            …
                                Удалить   🗑        ← низ-право шапки (у нижней границы)

  зафиксирован             Расфиксировать   🔓     ← верх-право; корзины нет
  ```

  **Два слота разнесены по вертикали:** режим+фиксация — сверху справа, корзина — у
  **нижней границы шапки** (на уровне последней строки свойств), не в плотную колонку
  сверху. Корзина подписана «Удалить», как и остальные контролы.

  **Корзина — только в режиме ПРАВКИ** (уточнено 2026-07-22): в просмотре её нет вовсе.
  Так просмотр чист, случайное удаление структурно невозможно (нельзя удалить, не войдя
  в правку), и заодно снят частный казус «прилипшей» корзины у форм без блока свойств
  (проект в просмотре): нет свойств — нет и низа шапки, но корзины там и так уже нет.

  У зафиксированного документа контрол **ровно один** — «Расфиксировать». **Корзины
  под замком нет:** движок всё равно откажет удалить запертое («сперва расфиксируйте»),
  а мёртвая кнопка спорила бы с принципом «состав контролов = степень свободы».
  Удалить можно только расфиксированный документ, войдя в правку — тогда корзина и
  появляется. Интерфейс показывает степень свободы своим составом.

- **Карандаш на «Расфиксировать» не ставим.** Карандаш принадлежит оси представления,
  замок — оси данных; совместив их на одной кнопке, мы бы снова слепили две оси,
  которые волна 19 специально разводила (по той же причине отвергнуто слово
  «Запереть»). Пара `🔒`/`🔓` — одна ось, два направления.

- **Расфиксация делает только своё:** снимает замок с документа и **оставляет форму в
  просмотре**. Прежняя формулировка «после согласия документ — черновик, форма сразу
  разлокована» отменяется: она противоречит принципу «правка — всегда явное решение».
  Порядок теперь: расфиксировал → документ стал черновиком → отдельным решением нажал
  «Редактировать».
- **Корзина — в правом НИЖНЕМ углу шапки**, в собственном постоянном слоте.
  Мнемоника: удаление — часть шапки документа; строки документа и BOM живут сами по
  себе, поэтому в их зоне корзине не место.
  **Чем это отличается от того, что чинили в волне 16:** тогда корзина появлялась
  **в том же слоте, что и замок**, и сдвигала его — кнопка под курсором менялась на
  лету, отсюда и промахи. Вынос в плавающую кнопку был лечением симптома. Правильное
  лечение — **дать корзине свой слот**, отстоящий от слота режима: слот режима
  перестаёт быть плавающим, корзина всегда в одном месте. Оба слота в шапке, но
  разнесены по вертикали (режим — верх, корзина — низ). Удаление остаётся под `confirm`.
  **Корзина — только у расфиксированного и только в режиме правки** (см. макет выше):
  под замком и в просмотре её слот пуст.
- **«Скачать» живёт в том же нижнем слоте, НАД корзиной** (уточнено 2026-07-30). До
  этого дня правило звучало «в слоте корзины у зафиксированного» — оно держалось
  ровно потому, что кнопка была одна (бланк закупки), и слоты не сталкивались. С
  выгрузкой изделия столкнулись: состав нужен и черновиком, а покупной компонент не
  фиксируется вовсе (`synced ⟹ not locked`) — «только у запертого» оставило бы его без
  кнопки навсегда. Поэтому:
  - **обе команды могут стоять вместе**; корзина остаётся самой нижней (её место
    неподвижно — ради этого слот и заводили), «Скачать» встаёт над ней;
  - **видимость «Скачать» решает ФОРМА, а не слот**: у закупки бланк даётся только
    зафиксированной (документ наружу — до фиксации план ещё не решение), у изделия —
    всегда.
- **Несколько целей выгрузки → меню** (2026-07-30). Кнопка та же, но открывает список
  вариантов: у изделия это «Только состав» / «Все вкладки» / **«Отмена»**. Слой и знак
  строки — от пикера (`AnchoredMenu` + `.typeahead-item`), глиф пункта = глиф ВКЛАДКИ,
  которую пункт выгружает (§2). «Отмена» — своя строка, а не только Esc и клик мимо:
  меню из трёх пунктов закрывают тем же движением, каким открыли.
- **Дефолт «просмотр» распространяется на ВСЕ формы.** На 2026-07-20 канону следовали
  только Изделие, Место и Дефицит; ордера, Закупка и Заказ открывались в правке
  (`useFormLock(true)`) — дрейф кода от канона, чинится в Ф9.

**Фиксация документа** (posted/closed; в README-модели — «мягкий замок») —
смысловая, общая для всех, живёт в данных. Слово-объединитель всех
терминальных статусов: проведённая поставка, проведённая комплектация,
закрытый проект — всё это «документ **зафиксирован**».

- Зафиксированный документ: в колонке контролов — **единственная кнопка
  «Расфиксировать 🔓»** (не чип-с-заливкой — устарело с Ф9: контролы стали единой
  колонкой Codicon), вся форма read-only, в мета-строке — серый глиф 🔒,
  индикатора сохранения нет (индикаторы сняты, см. выше).
- Клик по «Расфиксировать» **предлагает снять фиксацию** — подтверждение **всегда**
  (короткое; при зависимых — развёрнутая модалка «поедут N зависимых»).
  После согласия документ — черновик. ~~Форма сразу разлокована~~ — **отменено
  2026-07-20** (см. уточнения выше): форма остаётся в просмотре, правка включается
  отдельным решением.
- **Фиксация — отдельная осознанная операция** («Зафиксировать», с
  валидацией), НЕ закрытие замка формы: снять фиксацию через колонку
  можно, поставить — тоже, но отдельной кнопкой. Кнопка «Зафиксировать» живёт
  **в колонке контролов шапки** (Ф9) — рядом с «Редактировать», у расфиксированного
  документа.
- У **справочника поставщиков** фиксации нет — только пара замка формы. У **изделия**
  фиксация есть (волна 17), но ставится не кнопкой формы, а синхронизацией с
  библиотекой; в шапке — только «Расфиксировать». Закрытый проект ведёт себя как документ.
- **Окружение** (проекции линзы) — read-only всегда, независимо от всего.

## 6. Редактируемость полей

Принцип: **редактируемо всё, что хранится в документе, — включая автора,
даты и структурные якоря** (проект документа, поставщик УПД, изделие-цель
комплектации). Жизнь заставляет: документ заводит один, а отвечает другой;
дату правят задним числом; поставку заводят не на тот проект. Исключений
ровно три: суррогатный **id**, **вычисленные проекции линзы** (правятся в
документе-факте) и поля **зафиксированных** документов — до снятия фиксации.

Смена якоря — обычное поле шапки под замком формы, но с последствиями по
данным (лоты поставки следуют за её проектом и т.п.): движок валидирует и
**отказывает с объяснением**, когда перепривязка уже небезопасна (зависимые
в других документах). Прежнее правило «якоря выбираются при создании и инлайн не
правятся» (UI_PRINCIPLES, Правило 1) этим **отменено** — окончательно закрыто Ф2k
(волна 13): якоря ⚓ правятся под замком, движок стережёт безопасность.

Подтверждённые дыры, закрываемые чистовым проходом:

- **Состав изделия (BOM)** — на форме изделия: редактируемая таблица «Состав»
  (компонент + количество, призрачная строка). Where-used остаётся read-only
  окружением. Сейчас BOM вообще не редактируется из интерфейса.
- **Состав проекта (потребность, `ProjectDemand`)** — на форме проекта:
  изделия + количества, та же механика.
- **Свойства изделия** (код, название, вид, единица) — под замком формы.
- **Шапки документов** (дата, номер, комментарий) — под замком формы.
- **Свойства лота** (цена, название из УПД, заводской номер, примечание).
- **Справочники** (поставщик, проект: реквизиты, бюджет, статус, название).

**Раздел ответственности замка (принят 2026-07-05).** На справочных формах
(изделие, проект) замок §5 закрывает **реквизиты/идентити в шапке** (у изделия —
артикул, название, вид, ед.изм., оценка, «производимое»; у проекта — название,
бюджет, дата начала). **Операционные списки — состав (BOM) и потребность
(`ProjectDemand`) — живут без замка**, правятся прямым автосейвом (как строки
форм). Логика: списки — ежедневный рабочий инструмент, идентити — редкая правка,
которую бережём замком. Фиксации (posted/closed) у справочных форм нет — только
интерфейсный замок. Реализовано: `estimated_cost` изделия и `budget` проекта — под
замком; BOM/потребность — живые.

`[ЗАКРЫТО Ф2i]` **Матрица полей** «форма × поле → всегда / под замком / read-only /
скрыто» — [FIELD_MATRIX.md](FIELD_MATRIX.md) (**архив** с 2026-07-30: роль выполнена,
порядок полей держит §13.4a + ER-диаграмма, редактируемость — сам код `update_*`).
Шесть документов-близнецов схлопнуты в
**один row-set единого «Ордера» (`StockDocument`)** с видимостью полей по `kind`
(раздел B матрицы: шапка + строка/born-лот) — это же спец единой формы `<OrderForm
kind=…>`. Канон ордера:

- **Шапка** (`project`/`user`/`date`/`number` — общие; `contractor`/`purchase`/
  `target_item`/`qty`/`reason` — специфика вида, с Ф14 в той же таблице): всё
  редактируемо под замком; `date`+`number` обязательны для всех видов кроме
  комплектации (`REQUIRED_HEADER_BY_KIND`, Ф2d); `project`/`contractor`/`target_item` —
  **якоря** ⚓ (движок валидирует, может отказать при зависимых).
- **Строка**: рождение лота (`item`/`qty`/`unit_cost`/`part_number`/`lot_name`,
  `predecessor` у инвентаризации) — редактируемо; ссылка-якорь (`lot`/`source_lot`/
  `component`) — класс `＋` (задаётся при добавлении, смена = удалить+добавить);
  перемещение несёт `from_location`/`to_location`.
- **Замок** — единый мягкий `status {draft⇄posted}` на всех видах; окружение (проекции
  линзы) read-only всегда.

«Свод расхождений» #A матрицы (правка якорей и авторства шапки на форме) **закрыт
целиком** 2026-07-10: авторство — Ф2j, якоря ⚓ — Ф2k. Очереди из матрицы не осталось.

### 6b. Выпадающий список (`Dropdown`; принят 2026-07-29, волна 19 Ф12d-добор)

**Все выпадающие списки продукта — один компонент** (`Dropdown.tsx`). Нативный
`<select>` рисует меню средствами ОС: системное синее выделение посреди тёмной темы,
своя метрика строки, свой шрифт. Пока таких списков было два, это не мешало; к волне 19
их стало **восемнадцать**, и половина интерфейса выглядела чужой. Решение Ивана:
«раз у нас есть кастомные формы, все выпадающие списки оформить в одном месте, чтобы
интерфейс выглядел консистентно и правился сразу везде».

- **Один знак на всё:** поле (`<input readOnly>` — чтобы правила ширины, замка и колонок
  действовали без единого нового селектора) + шеврон + меню в стиле `.typeahead-menu`.
  Выбранный пункт отмечен галочкой — тем же знаком, что в множественном выборе (Ф13).
- **Отличие от пикера (§6a) — одно:** в пикере НАБИРАЮТ (type-ahead сокращает большой
  справочник), в `Dropdown` выбирают из наличного, поэтому и появляется шеврон
  закрытого списка. Критерий выбора между ними — не размер справочника, а знает ли
  человек, что ищет.
- **Исключения ровно два:** type-ahead (`Picker`) и множественный выбор проектов.
- Клавиатура: `↓`/`Enter`/`Space` раскрывают, `↑`/`↓` ходят, `Enter` выбирает,
  `Esc` закрывает. Закрытие по клику мимо — сторожем на `pointerdown`, **не по `blur`**
  (§6a, урок 2026-07-29).
- **В списке выбора — ТОЛЬКО `code`** (решение Ивана 2026-07-29): склейка
  «КОД — описание» распирала поле и меню, а описание чаще дублирует код. Описание
  остаётся там, где оно помогает искать, — в строке type-ahead и в списках (§7a).
  Исключение — автор: у пользователя кода нет, его идентичность — имя.

### 6a. Пикер справочника (единый контрол выбора; принят Ф2, волна 19)

Любая ссылка на объект справочника выбирается **одним контролом** — `<select>` со
всем справочником нигде не остаётся. Правила:

- **Поведение:** вводишь `code` или `description` → список кандидатов сокращается
  (≤20) → `↑`/`↓` ходят, `Enter` выбирает подсвеченного, `Esc` закрывает, клик по
  строке выбирает. Второй `Enter` (меню закрыто) выполняет действие строки
  («добавить»). При пустом поле меню **не раскрывается**: пикер — инструмент поиска,
  а не витрина справочника (выбор Ивана 2026-07-25).
- **Строка кандидата — по §7a:** `[глиф][code] описание`. Глиф — только там, где у
  сущности есть ось состояния (изделие: замок/синк; заказ: замок). У контрагента оси
  пока нет — глифа нет: глиф без смысла есть декорация.
- **Меню не во весь экран:** ширина `min(680px, вьюпорт − поля)`, правая граница
  всегда видна и не прижата к краю окна. `code` не жмётся никогда, длинное описание
  обрезается многоточием в своей колонке. Отступ от края меню = зазору между
  колонками (8px): иначе глиф визуально отлипает от кода.
- **Колонки в меню НЕ выравниваем** (принято 2026-07-26) — сознательное отступление
  от §7a. Списки режима **сканируют** глазом, поэтому там колонки; меню пикера
  **читают** сверху вниз по одному кандидату, и воздух между коротким кодом и
  описанием только рвёт строку. `code` и описание идут встык через один зазор.
- **Подсветка всегда видна:** ход стрелками подтягивает список к подсвеченной строке.
  Прокручивается **только само меню** (границами `scrollTop`, а не `scrollIntoView`) —
  страница под пикером не должна дёргаться. Подсветка — смысл (ядро), прокрутка за
  ней — знак (тема).
- **Автовыбора первого варианта нет нигде.** Молчаливый первый вариант `<select>` —
  источник ошибочных документов (не тот прибор в комплектации, не тот поставщик в
  УПД). Выбор всегда явный, даже когда кандидат один.
- **Ввод не трогает выбранное.** Пока не выбрано новое, старое значение живёт;
  уход с поля возвращает текст выбранного. Поэтому на формах с немедленным
  сохранением набор текста не порождает PATCH и не блокирует поле (`busy`).
- **Очистка — отдельным действием** (`×` справа), и только там, где поле
  необязательно (контрагент закупки/передачи, заказ у поставки). Где ссылка
  обязательна, очистки нет.
- **Под замком формы** пикер — просто текст (`.form-locked` гасит рамку и
  `pointer-events`), `×` не показывается.
- **Меню ничем не обрезается и умеет раскрываться вверх** (боль Ивана 2026-07-28).
  Оно рисуется **порталом в `body`** с `position: fixed` и привязкой к прямоугольнику
  поля, поэтому его не режут ни панель табов (`overflow: hidden`), ни прокрутка
  страницы. Мало места снизу — меню идёт **вверх**; тесно с обеих сторон — жмётся по
  доступной высоте и скроллится внутри. Правило общее: **всплывающий слой не живёт
  внутри прокручиваемого контейнера**; `z-index` эту болезнь не лечит в принципе —
  `overflow` отрезает раньше, чем слои начинают спорить.

## 7. Списки режима

Единый шаблон для всех десяти режимов:

- Первым — призрачный пункт **«＋ Новая ‹сущность›»** (правило 1 канона).
- Строка списка: `глиф · моно-код` — везде одинаково. **Подписи нет** (не
  читалась, грузила интерфейс); полное название живёт на форме, а
  фильтр-строка ищет в том числе по названию, хоть оно и не показано.
- **Глиф есть у каждого режима** (актуально с Ф1b/Ф3a — глиф ⟂ цвет: форма глифа
  несёт «что это», цвет — «как идут дела»):
  - *Изделия* (`native=true`) — **замок** `lock`/`unlock` (ось фиксации), цвет =
    фиксация (зелёный заперт / оранжевый открыт);
  - *Компоненты* (`native=false`) — **sync** (`sync` зелёный = из библиотеки /
    `sync-ignored` оранжевый = заведён вручную); замок у компонента в списке НЕ
    показываем (правило «ровно один глиф по режиму», Ф3a);
  - *документы* — тот же **замок** (ось фиксации); цвет = покрытие лотами у Заказов,
    worst-of по проекту у Проектов;
  - *проекты* — **замок** (активный/архивный) + цвет worst-of (линза): красный есть
    к заказу / оранжевый заказано-ждём / зелёный покрыто. Список проектов — мини-сводка
    линзы.
- **Один и тот же глиф Item «перетекает» с сущностью во ВСЕ списки**, где она
  встречается: справочник, состав (BOM), дерево дефицита, потребность, закупка. Правило
  выбора глифа — по `native` этой строки (компонент = sync, изделие = замок), а не по
  контексту списка (Ф3a; `ItemGlyph` в `status.tsx`).
- Сортировка: **документы — новые сверху** (зафиксированные приглушены),
  **справочники — по коду**.

### 7a. Вёрстка строки-списка (референс; копим правила для сквозной полировки)

Строки должны читаться как **ровная вертикальная колонка глифов** — это резко ускоряет
сканирование (проверено). Правила (референс волны 19; ордера/закупки/заказы приводим к
нему отдельным сквозным проходом позже):

- **Порядок символов:** `[раскрыватель (если есть)] · [цветной глиф] · [code]`.
  **Раскрыватель — Codicon `chevron-right` (свёрнуто) / `chevron-down` (раскрыто)**,
  единый везде (полировка 2026-07-26; текстовые ▸/▾ сняты). Компонент `Chevron` в
  `status.tsx`, размер — компаундом `.ci.chv` (13px, как у `.sg`: базовые 18px рвут
  высоту строк).
  Глиф — первый *значимый* символ строки, сразу после треугольника-раскрывателя и прямо
  перед кодом.
- **`code` — всегда одной строкой**, длинный обрезается многоточием (`nowrap` +
  `text-overflow: ellipsis`), НЕ переносится. Перенос ломал высоту строк и рвал ровную
  колонку глифов.
- **Строки одной высоты, без разрывов** — глиф идёт за глифом без увеличения
  вертикального интервала. Никаких `margin-top` на отдельных типах строк (device-строки
  дефицита разъезжались с «Потребностью» из-за `margin-top:6px` — снято). Секции целиком
  разделяет заголовок секции, а не воздух между строками.
- **Тонкая серая полоса-разделитель** (`border-bottom: 1px var(--border)`) — у ВСЕХ
  строк-данных единообразно (и «Приборы», и «Потребность»), не у избранных типов.
- **Отступ вложенности:** в древовидных списках весь ведущий блок
  `[chevron][глиф][code]` **отступает единым блоком** по глубине — раскрыватели идут
  ступенькой и показывают вложенность (дочерние — правее родителя; поддерево живёт под
  своим родителем, `indent = (depth+1)·шаг`).
- **Структура строки — фиксированные КОЛОНКИ, каждое поле в своей:**
  `[глиф] [code]` (ведущая ячейка) │ `[description]` │ `[числовые/статусные колонки:
  надо · разбор · склад · …]` │ `[действия]`. `code` и `description` — **разные
  колонки**, выровнены по вертикали через все строки; описание — серым, обрезается
  многоточием в своей колонке.
- **АНТИПРИНЦИП (не повторять):** `code` и `description` слитой одной строкой-абзацем
  в одной ячейке (`«BGB707… усилитель мощности…»` встык) — так сейчас в форме Заказа
  (`PurchaseView`) и это плохо: глаз не цепляет колонки, коды не выравниваются, скан
  ломается. Всегда — раздельные колонки (см. выше). Заказ/Закупку/Ордера приводим к
  этому сквозным проходом позже.
- **Описание сжимается ПЕРВЫМ, во всех списках** (принято 2026-07-29, Ф12d — долг Ф5).
  Колонка описания помечается `c-desc` и не задаёт таблице минимума (`max-width: 0`),
  поэтому лишний текст уходит в многоточие, а таблица не вылезает за край панели;
  служебные колонки (`c-fit`, числа, команды) жмутся по содержимому. Раньше правило
  стояло точечно (класс `tight` у двух списков), а остальным описание резали магические
  600 px — в узком окне таблица всё равно вылезала, в широком колонка не добирала.
  **Разметка колонки — часть канона:** таблица без `c-desc` выпадает из правила и
  распирает панель (так и было в «Составе» и «Применении» изделия — именно из-за них
  общую правку в Ф5 откатили в точечную).
- **ЦВЕТ ЯЧЕЙКИ — ПО ОСИ «ИДЕНТИЧНОСТЬ / КОНТЕКСТ»** (записано 2026-07-30, волна 21 Ф3;
  правило сложилось само задолго до этого и жило 62 инлайнами):
  > **Полным цветом — идентичность и счёт** (коды, номера, числа). **Приглушённо —
  > проза и даты** (описание, дата, имя контрагента, имя проекта, `part_number`,
  > `lot_name`, автор).

  Это **та же ось, по которой разведены шрифты** (§3: JetBrains Mono — идентифицируемое
  и счётное, Inter — литературное), поэтому нового решения она не требует.
  Реализация — **умолчанием, а не утилитой**: `table.grid td` приглушён, полный цвет
  возвращают роли `.c-key` / `.num` / `.code` (плюс `.seg` — разбор счётный). Ячейка,
  которой цвет нужен, называет **свою роль** (`.code` = «здесь идентичность»), а не
  цвет: утилита `.dim` на 62 места отвергнута — она зацементировала бы расхождение.
  Своего цвета держатся `a.link`, поля ввода, `.hint` / `.anomaly` / `.kind-chip`;
  **призрачная строка приглушена целиком** — черновик остаётся черновиком во всех
  колонках. Разъехалось же оно из имени класса: `.c-fit` названа по вёрстке («жмётся по
  содержимому»), и в неё свалили и коды, и даты, и имена — цвет каждой дописывали рукой.
- **Колонка идентичности — одной ширины во всех формах** (`--col-key`, 200px ≈ 25
  моно-знаков; волна 21 Ф3). `width` в таблице — только пожелание: при
  `table-layout: auto` соседняя `c-desc` («беру весь остаток») всегда перетягивала спор,
  и колонка садилась на min-content своей таблицы — отсюда разнобой ширин по формам.
  Держат три свойства вместе: `min/max-width` (снимают спор) + `nowrap` (дефис в
  `3221-10-0200-00` перестаёт быть точкой переноса) + `ellipsis`. **Тултипа на
  обрезанном коде нет намеренно:** код — короткий жаргон, и многоточие это сигнал «чини
  код, а не колонку». Ячейка, накрывающая несколько колонок (`colSpan`), из зажима
  исключена — она уже не эта колонка.
- **Колонка глифа: отступ от края = отступу глиф→код** (принято 2026-07-26). Иначе
  глиф прилипает к рамке панели и ровная вертикаль глифов читается хуже. Колонка —
  по содержимому, правый паддинг отдаёт соседу (`.gl`).
- **Заголовок списка = ПЕРВАЯ СТРОКА, а не подпись** (принято 2026-07-26): тот же
  кегль и **та же высота**, что у строк-данных (общий `line-height`), отличается
  только приглушённым цветом — и тем, что ссылок в ней нет. Первая строка, которая
  выше остальных, читается как шум. Мелкий шрифт (11px) читался как «мелкая подпись» и
  терялся. Выключка заголовка = выключка его колонки (числовые — вправо).
  `[РАЗВИЛКА, в бэклоге]` вариант «заголовок по центру колонки» — Иван сомневается.
- **Единица измерения — ВСЕГДА своя колонка, крайняя правая** (принято 2026-07-26;
  давняя боль). Исключение ровно одно: правее могут стоять только **функциональные
  кнопки** строки (`×`, «добавить»). Единицу НЕ приклеиваем к числу внутри ячейки
  кол-ва — там она пляшет от разрядности числа и путается. Подпись колонки —
  **«Ед.»** (проверено в деле 2026-07-26: короткая подпись легла лучше длинной,
  которая была длиннее самих значений); значение выключено влево (примыкает к своему
  числу), цвет приглушённый. Правило действует **во всех списках, где есть считаемое**
  (не только там, где единица разная: «шт» встречается чаще всего, но колонка всё
  равно своя).
- **Глиф — в КАЖДОМ списке, где строка про сущность** (принято 2026-07-26). Форма
  глифа = что это, цвет = как дела (§7a, ось ⟂ ось). Раскатано: изделие/компонент —
  `ItemGlyph` (замок либо синк), ордер — `StatusGlyph` (замок), вложение —
  **`FileGlyph`**: форма по расширению (`file-pdf` / `file-media` / `file-code` /
  `file-binary` / `file-zip` / `file`), цвет — живо ли оно на диске (зелёный —
  совпадает с записью, оранжевый — размер/время разошлись, файл перезаписан мимо
  Plume, красный — записи есть, файла нет). **Партия — `LotGlyph`** (принято
  2026-07-26, Ф12c): своей оси состояния у лота нет, поэтому ФОРМА = откуда партия
  родилась (`inbox` поставка · `tools` изготовлено · `checklist` найдено
  инвентаризацией · `git-branch` отпочковано требованием), ЦВЕТ = живость остатка
  (зелёный есть · приглушённый исчерпана · красный минус = недостача). Текстовый чип
  «origin» после этого лишний — вид рождения несёт сам глиф.
- **Команда внутри строки** («Скачать», «Удалить» у вложения) оформляется **как команда
  шапки** (`.fh-ctl`: глиф + подсветка фоном), только компактнее и **одним глифом** —
  подпись живёт в `title` (принято 2026-07-26): в списке команд много, текст на каждой
  строке шумит. Своего языка кнопок у строк нет.
- **Удаление строки — всегда кнопка-корзина** (`trash` в стиле команд, ховер в
  семантическом цвете), а не текстовый крестик `×` (принято 2026-07-26). Одно действие —
  один знак: та же корзина, что удаляет сущность в шапке формы, убирает и строку из
  списка. Крестик `×` остаётся **только за очисткой поля** (`×` у пикера, §6a) — это
  другое действие, и путать их знаками нельзя.
- **Подчёркивания у команд нет нигде** (принято 2026-07-26) — ни в покое, ни на ховере.
  Подчёркивание — знак ссылки-текста, у команды знак другой: глиф и подсветка.
- **Удаление строки — только в режиме ПРАВКИ** (принято 2026-07-26): то же правило,
  что у корзины шапки (§5) — просмотр чист, случайное удаление структурно невозможно.
  Безопасные команды строки («Скачать») доступны всегда.
- **Одинаковые колонки стоят на одном месте во всех табах формы** (принято
  2026-07-26): колонка идентичности (код / имя файла / номер ордера) имеет общую
  ширину-токен (`--col-key`), поэтому при переключении табов соседняя колонка описания
  не переезжает. То же уже работало для правого края («Кол-во», «Ед.») — теперь и слева.

  **Ширина колонки кода ПРИБИТА, и это единственный способ её удержать** (правка
  2026-07-30, реализация — волна 21). До неё правило существовало только на бумаге:
  `width` в таблице при `table-layout: auto` — **пожелание, а не размер**, браузер делит
  ширину по содержимому. Рядом `td.c-desc { max-width: 0; width: 100% }` прямо заявляет
  «беру весь остаток», колонка кода проигрывает этот спор всегда и садится на минимум,
  посчитанный от содержимого **конкретной** таблицы — отсюда разная ширина в каждой форме.
  Держится только тройкой `width` + `min-width` + `max-width`.

  **Код — всегда одна строка, лишнее в многоточие** (`white-space: nowrap` +
  `text-overflow: ellipsis`). Без `nowrap` код рвался **по дефисам** (`3221-10-0200-00` в
  четыре строки, `MT9V024IA7XTM-DP` в две), раздувая высоту строки: дефис — законная точка
  переноса, и min-content такой ячейки считается по куску между дефисами.

  **Тултипа на обрезанном коде нет** — намеренно. Код обязан быть коротким жаргоном
  (§13.5, «код = первичная идентичность»), и обрезание — сигнал чинить код, а не колонку;
  тултип этот сигнал заглушает. Исключение по природе — имя файла во вкладке «Файлы»:
  оно коду не подчиняется.
- **Ширину забирает ОПИСАНИЕ, а не служебные колонки** (принято 2026-07-26):
  описание тянется на весь свободный остаток (`.c-desc`), а размер / даты / автор
  жмутся по содержимому (`.c-fit`) и уезжают вправо, к командам строки. Иначе между
  обрывающимся описанием и числами остаётся мёртвое поле. **Поле ввода внутри такой
  колонки тянется вместе с ней** — inline-`width` у контрола сильнее любого класса,
  поэтому ширину ему не задаём вовсе и оставляем решать CSS (та же болезнь, что
  «ютящееся описание» в шапке, §13.3). Выключка в такой колонке — **влево**: описание
  это текст, а числовой контрол по умолчанию выключен вправо и уезжает к соседям.
- **Замещающий текст пустого списка дышит одинаково сверху и снизу** — иначе липнет
  к полосе табов.
- Полное имя/`description` — на форме и в фильтре-поиске (в справочных списках-сайдбарах
  описание не показываем вовсе; в табличных списках дефицита/потребности — отдельной
  колонкой).
- Группировки по проекту нет («все УПД одинаковые»).
- Над списком: **фильтр-строка** (сужение по коду/названию по мере набора)
  и **дропдаун-фильтр по проекту** — во всех режимах, где у объекта есть
  проект (сценарий: при закрытии проекта прощёлкать все его поставки);
  для многопроектных Закупок-план фильтр читается как «затрагивает проект».
- **Раскладка фильтров — одна на все режимы** (ревизия 2026-07-30): фильтр-строка во
  всю ширину списка, под ней — строка выпадающих; **один занимает её целиком, два
  делят пополам** (образец — «все типы · все проекты» у Ордеров). Края всех контролов
  совпадают с краями списка: разнобой ширин читается как поломка, а не как акцент.
  Выпадающий появляется, только когда есть из чего выбирать (одно значение — не выбор).
- **Цвет ячейки идёт по оси «идентичность / контекст»** (принято 2026-07-30, реализация —
  волна 21). **Полным цветом — идентичность: коды, номера, числа. Приглушённо (`--fg-dim`) —
  проза и даты.** Это **та же ось, по которой разведены шрифты** (§3: моно —
  идентифицируемое и счётное, Inter — литературное); новой оси не заводим, цвет просто
  идёт по существующей.

  Выражено **инверсией умолчания**, а не пометкой каждой ячейки: приглушённый — базовый
  цвет `td`, полный цвет — свойство `.c-key` / `.num` / `.code`. Два правила в CSS вместо
  62 инлайновых `style={{ color: 'var(--fg-dim)' }}`, которые до этого расставлялись
  руками по одной ячейке (и разъехались: `contractor_name` и `lot_name` встречались и
  приглушёнными, и нет).

  **Утилиту `.dim` не заводим.** Класс-по-цвету зацементировал бы расхождение и добавил
  исключений вместо того, чтобы их убрать (принцип Ивана: «мало стилей, понятная иерархия,
  минимум исключений»).

  **Диагноз на будущее — имя класса решает.** `.c-key` и `.c-desc` названы по **роли** и
  не разъехались; `.c-fit` названа по **поведению** («жмётся по содержимому»), в неё
  свалили коды, даты и имена вперемешку — и цвет пришлось дописывать руками. Колонку,
  названную по вёрстке, оформление обходит стороной: **роль называем ролью**.

## 8. Навигация и поиск

- **Переходы по связям**: любое упоминание объекта (лот в строке поставки,
  изделие в дефиците, документ-origin) — кликабельно, ведёт на его форму.
  Последовательно везде, а не местами.
- **ЯКОРЬ ШАПКИ — ТОЖЕ упоминание объекта** (уточнено по добору Ф17, 2026-07-30). Якорь,
  указывающий на сущность **со своей формой**, обязан быть ссылкой в просмотре: под
  замком поле = сама ссылка, отдельной кнопки «открыть ›» не нужно. Так живут «Проект»
  (все формы), «Закупка» заказа, «Заказ» поставки, «Изделие» комплектации, охват закупки.
  Проверять при заведении **каждого** нового якоря, а не по замечанию на приёмке.
  Единственное законное исключение — сущность, формы у которой в продукте ещё нет
  (сейчас это контрагент: режим «Контрагенты» — волна 20).
- **История**: «назад» к предыдущей форме (уже есть) — сохраняется.
- **Палитра ⌘K**: глобальный поиск-переход по коду/номеру/названию из любого
  места; позже туда же лягут команды-действия.

## 9. Действия над объектами

**Закрыто решением задним числом 2026-07-30** (аудит-1, Б4-3). Инвентарь действий так
и не собирали — и не нужно: ответ устоялся сам, ровно по правилу «≤3 действия — кнопки
на месте допустимы». Фиксируем факт как канон.

**Две поверхности, третья не заведена:**

1. **Колонка контролов в заголовке формы** (`FormHeader`, §5) — всё, что относится к
   объекту целиком: замок формы, «Зафиксировать» / «Снять фиксацию», «Скачать»
   (с меню, если вариантов несколько), корзина. Каждый контрол — «подпись + Codicon»,
   видимость подчинена замку и фиксации.
2. **Глиф-команда в строке** — колонка `.act` в конце строки таблицы: одно действие
   (обычно 🗑 удалить строку/вложение), появляется только когда форма правима. Это
   допущенное «иконки по наведению», а не возврат к кнопкам на каждой строке
   (§0.2): контрол один, в фиксированном месте, для серийного удаления.
3. **Контекстное меню по правому клику** — **не введено и не планируется.** Смущало в
   вебе с самого начала, потребности не возникло: сложных операций на форме нет,
   сложность живёт в движке и объясняется отказами. Палитра ⌘K (§8) закрыла быстрый
   путь навигацией.

### 9.1. Ответственность человека не подменяется автоматическим шумом

**Принято Иваном 2026-07-26** (при разборе охвата закупки, WAVE19 Ф13; перенесено из
UI_PRINCIPLES «Правило 4» 2026-07-30). Когда процесс **редкий и важный**, за ним и так
стоит внимание человека — предупреждать его автоматикой не нужно. Формулировка Ивана:
«"забыть закупиться на проект" звучит как "мы вообще закупкой не занимались"».

Признаки, по которым предупреждение **не заводится**:

- **Процесс редкий и ответственный** (закупка, фиксация, закрытие проекта) — человек
  находится в нём осознанно, а не проскакивает мимо.
- **Обратная связь уже приходит нормальным путём.** Незакупленное проявится само:
  закупка разрешится в заказы, заказы зафиксируются, и в своде проекта компоненты
  станут оранжевыми. Штатная цепочка статусов — уже и есть сигнал.
- **Предупреждение требует «разведки вбок»** — подглядывания в соседние сущности
  (проекты, чужие закупки), чтобы сказать «а вон там ещё что-то есть». Такая разведка
  расширяет область экрана за пределы того, чем человек сейчас занят, и превращается
  в фоновый шум.

Это не запрет на валидацию: движок по-прежнему **отказывает с объяснением**, когда
операция небезопасна. Правило — про **непрошеные советы** в тех местах, где ничего не
сломано, просто «могло бы быть иначе».

## 10. Цвет и тема

**Тем ровно две** (принято 2026-07-30, реализация — волна 21): **Тёмная** (слаг `dark`) и
**Светлая** (слаг `light`). Обе — дефолтные темы VS Code, **Dark 2026** и **Light 2026**,
парные по построению: контраст в них калибровала одна рука, поэтому таблица ниже ложится
строка в строку. Источник значений — `extensions/theme-defaults/themes/2026-dark.json` и
`2026-light.json` в репозитории VS Code.

Ярлыки в интерфейсе — **«Тёмная» / «Светлая»**, без «2026»: интерфейс русский, а версия в
подписи со временем соврёт (VS Code выпустит следующий дефолт). Родословная живёт здесь,
в документации, а не в кнопке выбора.

### 10.1. Два слоя, и это главное

- **Структура — одна на все темы** (`index.css`): раскладка, ширины, `nowrap`, многоточие,
  и **кто приглушён по роли** (§7a). Правила оперируют **токенами**, а не значениями.
- **Значения — по теме** (`themes/dark.css`, `themes/light.css`): только присвоения
  переменным. Переключение — атрибут `data-theme` на корне.

Отсюда следствие, ради которого всё и затевалось: правило вида
`table.grid td { color: var(--fg-dim) }` пишется **один раз** и даёт верный результат в
обеих темах. Новая тема = один файл значений + строка в реестре, ноль правок разметки.

hover и выделение строки. Это же и есть ловушка, которую снимает разделение слоёв: альфа
живёт в значениях, а не в правиле.

**Статусы `--st-*` в светлой темнее и насыщеннее** — на белом фоне пастель тёмной темы
(`#89d185`, `#cca700`) не читается. Значения — из `charts.*` и `problemsWarningIcon` темы
Light 2026, то есть тоже калиброванные, а не подобранные нами.

### 10.3. Правила, не зависящие от темы

- **Цвет — только смыслу.** Монохромные Codicons это правило поддерживают.
- Словарь статусов ● ▲ ✓ 🔒 ○ — общий (§0.4). **Смысл движковый, значение
  темино** ([[engine-view-seam]]): движок отдаёт `ok` / `wip` / `to_order`, тема решает,
  каким цветом это выглядит.
- Отдельного, более серого фона у панели режимов нет ни в одной теме (в обеих 2026
  активити-бар и сайдбар — один тон); зоны разделяются границей `--border`.
- Расшифровка 🔒 читается как «зафиксировано» (бывш. «заморожено замком») — словарь
  §0.4 приведён к этому слову 2026-07-30.

## 12. Заголовки секций внутри формы

Внутри формы объекта (не путать с заголовком формы §4) секции — это `.section-h`:
приглушённая капитель с нижней границей. Правило:

**Заголовок секции — одна строка: НАЗВАНИЕ + мета-информация.** Не описание того,
что это, а счётные факты о содержимом секции — то, ради чего на неё смотрят.
Вторых строк-подзаголовков под секцией не заводим.

```
ПРИБОРЫ        типов приборов 2 · всего приборов 13
ПОТРЕБНОСТЬ    типов компонентов 5 · всего штук 1020
СКЛАД ПРОЕКТА  живых лотов 4 · аномалий 1 ▲
```

- Название — капитель (как сейчас `.section-h`); мета — приглушённый `.hint`
  справа в той же строке, Inter, разделитель `·`.
- Мета = «сколько типов · сколько всего» (или ключевой статус секции: «пусто»,
  «закрыт {дата}»). Числа — счётные; аномалии/предупреждения — красным хвостом.
- Формы существительных фиксированные («приборов», «компонентов», «лотов») —
  не склоняем по числу, читается ровно при любом значении.

## 13. Канон формы (единый лэйаут всех форм; принят 2026-07-26, волна 19 Ф12)

**Решение Ивана:** у всех сущностей — **одна форма на всех**. Не «похожие формы», а
буквально один компонент-лэйаут (`FormShell`), в который формы вставляют своё
содержимое. Это продолжение чистки, начатой на полях (`code`+`description`, волна 19
Ф10/Ф3): там свернули зоопарк ручек, здесь сворачиваем **зоопарк форм**.

Источник вдохновения — окно агентов VS Code и Telegram (любимые программы Ивана):
панели-карточки со скруглением и табы, переключающие содержимое.

### 13.1. Анатомия — вертикальный стек

```
                        3220-10-0100-00                 ← титул = code, по центру
   ┌──────────────────────────────────────────────────┐
   │ Код         [3220-10-0100-00     ]  Редактировать ✏ │  ← ШАПКА: поля | команды
   │ Описание    [Диагностическая вилка на плату…    ]  Зафиксировать 🔒 │
   │ Категория   [connectors          ]               │
   │                                        Удалить 🗑 │
   └──────────────────────────────────────────────────┘
   ┌──────────────────────────────────────────────────┐
   │ панель-дополнение (интеграл: бюджет / поставки)  │  ← если есть
   └──────────────────────────────────────────────────┘
            библиотечное · спящий · позиций 12          ← мета, по центру, НАД табами
   [⊞ Состав] [⚑ Где применяется] [▤ Партии] [🗎 Файлы]  ← табы
   ┌──────────────────────────────────────────────────┐
   │  список активного таба                            │  ← СПИСОК
   └──────────────────────────────────────────────────┘
```

Порядок сверху вниз, **одинаковый на каждой форме**:

1. **Титул** — `code` сущности.
2. **Панель «Шапка»** — поля слева, команды справа.
3. **Органичные дополнения** — панели интеграла (бюджет проекта, стороны контрагента),
   если они на этой форме есть.
4. **Мета** — по центру, **непосредственно над полосой табов** (ниже дополнений).
5. **Табы** — по одному на список формы.
6. **Панель «Список»** — содержимое активного таба.

К главным частям возможны **органичные дополнения** (панель бюджета на форме
проекта) — отдельной панелью в том же стеке, по той же карточной раскладке.

### 13.2. Панель-карточка

Обе главные части — карточка: `1px solid var(--border)` + скругление +
`background: var(--bg-side)`. Стиль не изобретаем: он уже есть у панели бюджета
(`.budget`), поднимаем его в общий класс.

**Радиус:** важен сам факт скругления, величина вторична (решение Ивана 2026-07-26).
Telegram-масштаб («огромные») отвергнут; ориентир — окно Claude Code. Живёт **одним
значением в одном месте** — заболит, правится в одну строку.

### 13.3. Шапка: две зоны в одной горизонтали

- **Слева — поля**, прижаты к левому краю; строка поля **тянется почти до колонки
  команд**. Длинное описание не должно ютиться в узкой строке.
- **Справа — колонка команд** (§5: режим формы, «Зафиксировать», «Удалить»,
  «Загрузить», «Скачать»).
- Зоны **визуально не разделяются** (ни рамки, ни фона между ними) — их разводит
  сама выключка: поля влево, команды вправо.
- **Ширина поля не задаётся в вьюхах.** Пиксельные `width={240}` в формах —
  антипаттерн, который и создал «ютящееся описание»; при переезде на `FormShell`
  выпиливаются. Ширина живёт **двумя токенами темы** (уточнено 2026-07-26):
  обычное поле (`--field-w`) и длинное (`--field-w-wide`, вдвое) — форма только
  выбирает ступень (`<dd className="wide">` у Описания). «Во всю оставшуюся ширину»
  пробовали — вышло слишком длинно, поле теряет край.
- **Колонка меток — по самой длинной подписи ЭТОЙ шапки** (`max-content`), не общей
  фиксированной ширины: у форм с короткими подписями фикс оставлял пустой коридор.
- **Значение поля выключено ВЛЕВО, к своей подписи** (принято 2026-07-26). Подпись
  прижата вправо, значение — влево: пара читается как одна строка. Выключка вправо
  (наследство числового `.qty-in`) разрывала пару через всю ширину панели и
  смотрелась плохо. Правило одно на все поля шапки, включая числовые.
- **Высоту шапки задают ПОЛЯ, не команды** (принято 2026-07-26). Колонка команд
  растянута на высоту шапки: **первая команда идёт в одной строке с первым полем**,
  а нижняя (корзина/«Скачать») — **в одной строке с последним**. Строки команд той же
  высоты, что строки полей; отдельного резерва места под корзину нет.

**Единица строки шапки (принята 2026-07-29, волна 19 Ф12d).** Высоту строки задаёт
**один токен темы** (`--row-h`), шаг строки — `--row-h + --row-gap`; ему подчинены
**все** элементы шапки: текст, инпут, дата, селект, пикер и кнопки-команды. До этого
высоту задавал сам контент — замер дал в одной шапке шаги 22 / 23 / 25 / 26 / 27 /
28 px: текст 16, инпут 20, дата и селект 22, команда 26. «В одну строку» сходилась
только первая пара, дальше расхождение копилось — ровный грид из этого не получался
**по построению**. Правила:

- **Единица одна на тему, не на форму.** Появился новый контрол — он подчиняется
  единице, а не заводит свою высоту.
- **Строка не ниже единицы, но может вырасти**, если значение перенеслось (охват
  закупки — коды проектов рядом с пикером): жёсткая высота обрезала бы содержимое.
- **Ширина — только двумя токенами** (см. выше), включая пикер: у него своя обёртка
  вокруг инпута и «×», и без явной ширины он был единственным полем, не слушавшим
  токен (336.8 px против 320).
- **Пиксельная ширина в JSX запрещена в шапке** — инлайн-стиль сильнее любого класса
  и выбивает поле из сетки (последний случай — «Образцов» у комплектации, `width={72}`).

**Просмотр — чистый текст, ОДНИМ механизмом (принято Иваном 2026-07-29).** §5 говорит
буквально: под замком поля ввода нет вовсе. До Ф12d это жило двумя разными способами —
одна форма (Изделие) рисовала настоящий текст, одиннадцать держали контрол в DOM и
гасили ему рамку классом `.form-locked`. Отсюда и разъезжались высоты, и шрифт значения
менялся вместе с режимом. Теперь развилку решает **один компонент** — `Field`/`TextField`
(`FormField.tsx`), вьюхи о ней не знают. Следствия:

- **Шрифт шапки — ТОЛЬКО Inter** (решение Ивана 2026-07-29; отменяет принятое в тот же
  день «шрифт от смысла поля», где коды и даты шли моноширинными). Моно вперемешку с
  литературным внутри одной панели сбивает: колонка значений читается как разнородная.
  Моно остаётся там, где оно работает на сканирование — титул формы, списки, мета.
  Один кегль на все значения, поэтому режим меняет только рамку вокруг значения.
- **Пустое значение — прочерк**, а не пустое место: пустота читается как «поля нет».
  Правило действует **внутри продукта**. В документе НАРУЖУ (xlsx-бланк закупки) оно
  переворачивается: незаданная графа не рисуется вовсе — у получателя пустая графа
  читается как брак, а не как «значение не задано» (уточнено Ф4b, 2026-07-30).
- **Дата в просмотре — `дд.мм.гггг`** (в правке остаётся `input[type=date]`).
  Тот же формат и в документах наружу (`engine._doc_date`) — ISO у поставщика не видят.
- **Замок формы гейтит шапку у ВСЕХ форм.** У Закупки и Заказа поля шапки правились
  в просмотре — «просмотр» значил у них не то же, что у остальных; выровнено.
- **Перечисление ссылок в поле — через ЗАПЯТУЮ, и запятая не ссылка** (охват закупки).
  Так видно, что перечислено несколько сущностей, а не одна с длинным кодом. Отступ
  от поля ввода — только в правке: в просмотре он выбивал значение из левой кромки.

### 13.4. Код и Описание — на каждой форме

Первые два поля шапки **везде, без исключений** (закреплено после волны 19 Ф10/Ф3b —
пара `code`+`description` есть у каждой сущности). Правило записано, чтобы не
потерялось при добавлении новых форм.

**ПОЛЕ ЖИВЁТ ТАМ, ГДЕ ПРАВИТСЯ** (обобщено 2026-07-30, волна 21 Р3; прежде правило было
записано частным случаем `Item.native`). Признак, который **задаётся вне этой формы**,
полем в ней не рисуем — ни как чекбокса, ни как read-only строки: поле обещает правку,
и поле, которое править нельзя, обещание не держит. Значение при этом не пропадает — оно
идёт в **титул** (§13.5) или в **мету** (§13.6), где ничего не обещает.

Случаи:
- **Ось режима.** Признак делит навигацию на режимы → задаётся тем, из какого режима
  сущность родилась. `Item.native` («Производимое»): «Изделия» рождают native,
  «Компоненты» покупное; поле снято с обеих форм и из «＋ Новый».
- **Задаётся в админке.** `User.username` — это `code` человека
  ([code-identity](../CLAUDE.md)), но логины заводит админка, а не форма аккаунта.
  Поэтому `username` **идёт в титул и полем не рисуется вовсе** (волна 21), хотя §13.4
  требует `code` первым полем: правило «поле там, где правится» сильнее.

То же
касается подписи: длинная подпись единиц → **«Единицы»** (в списках — короткая
**«Ед.»**, §7a), «Оценка, ₽» → **«Оценка»** (рубль
приезжает со значением в просмотре, дублировать его в подписи незачем).

### 13.4a. Порядок полей = порядок полей модели (принят 2026-07-29)

**ER-диаграмма README — источник порядка полей шапки.** Не «примерно похоже», а буквально:
поля идут в том порядке, в каком стоят в модели. Так порядок перестаёт быть вкусовым и
имеет ровно одно место, где его меняют.

Сам канон порядка (задан расстановкой Ивана в диаграммах):

**идентичность → замок → якори (связи) → внешние атрибуты → автор → специфика вида**

- `code`, `description` — всегда первые (§13.4).
- `locked` — в форме не поле, а команда (§5); в модели он стоит здесь, чтобы читалось
  «вот сущность, вот её замок, дальше связи».
- **Якори** (`project`, `purchase`, `procurement`, `contractor`) — одним блоком сразу под
  идентичностью: связи сущности важнее её атрибутов.
- **Внешние атрибуты** (`number`, `date`) — после связей: это юридическая обвязка.
- **Автор** — в конце: он про запись, а не про предмет.
- **Специфика вида** (`target_item`/`qty` комплектации, `reason` списания) — хвостом.

**Следствие для `OrderFields`: два слота, не один.** Специфика вида расщепляется надвое
так же, как в модели: якори вида (`purchase` и `contractor` поставки, `contractor`
передачи) идут в слот **между Проектом и Номером**, а атрибуты вида — в хвостовой слот
после Автора. Один слот «всё после общих полей» этот порядок выразить не может.

**При изменении порядка в диаграмме — переставить поля форм в том же изменении** (тот же
режим, что у правила «диаграммы = источник правды» в CLAUDE.md).

### 13.5. Титул = `code`

- **`code` вынесен из шапки** в отдельную строку над панелями, **по горизонтальному
  центру нижележащих панелей** (панели занимают всю ширину рабочего поля — экран
  минус колонка режимов минус колонка списка).
- Крупно, чисто, без глифов и без дополнений: **глиф состояния остаётся в мете**.
- **Пустой `code` — титул пустой** (решение Ивана 2026-07-26). Пустота давит и просит
  себя заполнить; мягкие фолбэки вида «Заказ #12» здесь **не показываем**.
- **Мягкое предупреждение при уходе с формы** с пустым или пробельным кодом:
  «Код оставлять пустым нельзя. Задайте поле Код или удалите {сущность}.»
  Предупреждение, не блокировка — схему не ужесточаем (`code` остаётся nullable,
  обязательность держится UI-подталкиванием, см. Ф11). Реализация Ф12a: срабатывает
  ровно на уходе (пока форма открыта, пустой титул давит и сам); удаление сущности
  предупреждение подавляет — ушедшую в корзину поминать не за что.

**Почему титул — именно код** (формулировка Ивана): «Сущность создаётся и меняется,
но то, что она есть и с ней ведётся работа, — главная ценность. Мёртвые сущности мы
стараемся удалять. Поэтому само существование такого кода — уже ценность».
См. также принцип «код = первичная идентичность» (волна 19, Ф11).

### 13.6. Мета

- **Слот базового лэйаута**: включается, выключается и переезжает **в одном месте**
  для всех форм сразу.
- Позиция — **по центру, вплотную НАД ПОЛОСОЙ ТАБОВ** (решение Ивана 2026-07-30):
  ниже панелей-дополнений, а не сразу под шапкой. Причина — содержимое меты: с
  2026-07-26 это счёт по табам в их порядке, то есть **спойлер того, что ждёт внутри**.
  Прижатая к табам, она читается как их оглавление; оторванная от них панелью
  интеграла — как продолжение шапки, и связь с табами терялась. От титула мета
  отделена по той же причине, по какой была вынесена из шапки (там она шумела).
  Отступы несимметричны намеренно: к табам ближе, чем к тому, что над ней.
- **Мета не повторяет поля** (правило принято 2026-07-26). Показывает только то,
  чего в полях нет: глиф состояния, вычисленные счётчики («позиций 12 · всего 4 300»),
  ключевой статус. Дублирование полей и было тем шумом, из-за которого мету не читали.
  Ср. §12 — то же правило для заголовков секций.
- **Счёт по табам живёт в мете**, а не в подписях табов (принято 2026-07-26). В табах
  числа шумели рядом с надписью, а мета без них выходила скудной и непонятно зачем
  нужной. **Порядок — как у табов**, число впереди подписи, со склонением (§3):
  «17 компонентов · 2 вхождения · 0 партий · 0 отгрузок · 0 файлов».
- **Мета дополняет счёт тем, чего в табах нет** — итогами документа. Итог в натуре
  сворачивается **по единицам** (штуки с метрами не складываем): «3 позиции ·
  10 344 шт · 50 м · 40 000,00 ₽ · 0 файлов».
- **Глифа в мете НЕТ** (принято 2026-07-26; отменяет прежнее «мета несёт глиф
  состояния»). Состояние сущности видно в списке режима и однозначно читается по
  доступным командам шапки («Зафиксировать» ⇒ расфиксировано). В форме глиф шумел.
- Признак **«спящий»** (ни одной живой ссылки на изделие — можно удалять) в мете
  остаётся: он шире любого счётчика (кроме вхождений — ещё лоты, строки заказов,
  потребность, комплектации). Обратное («используется») **молчит**: об этом уже
  говорят сами счётчики.

### 13.7. Табы

Несколько списков формы разрешаются **табами**, а не простынёй секций друг под другом.

- **Оформление — как у кнопок-команд шапки** (`.fh-ctl`): текст + глиф, подсветка
  фоном при наведении. Отличие: **глиф слева от надписи** (в командах — справа).
- **Табы живут в полосе вверху панели-списка** (принято 2026-07-26, образец — окно
  агентов VS Code): полоса **того же цвета, что тело панели**, отделена от него только
  тонкой границей. Табы и их содержимое читаются как ОДНА карточка; плавающие сами по
  себе табы путались с метой и шумели.
- **Активный таб подсвечен всегда**, и подсвечен **ровно как команда шапки под
  курсором** (`--bg-hover`): один язык подсветки на весь продукт, своего вида у таба
  нет (уточнено 2026-07-26).
- **Глифы табов берутся у РЕЖИМОВ навигации** (§2), когда таб про ту же сущность
  (принято 2026-07-26): состав → `chip` (Компоненты), применение → `rocket` (Изделия),
  склад → `layers` (Склады), отгрузки → `notebook` (Ордера), файлы → `files`. Один
  знак у одной сущности, где бы она ни встретилась.
- **Подписи табов — одним словом**, где язык позволяет: «Состав», «Применение»,
  «Склад», «Отгружено», «Файлы», «Строки».
- **Табы рисуем всегда**, даже если список один (решение Ивана 2026-07-26):
  единообразие и строгость дороже экономии строки. Двух разных видов формы быть не должно.
- **При смене сущности таб сбрасывается на первый** — тот же канон, что у замка формы
  (§5, Ф9: режим не должен перетекать между документами).
- **Счётчик строк живёт в самом табе** («Партии на складе 12»), реализация Ф12a.
  Внутри панели заголовка секции (`.section-h`) больше нет: он повторял бы надпись
  таба (§12). Число — моно, приглушённое; у таба без счёта (Файлы) его просто нет.
- **Набор табов может быть подвижен** (у покупного изделия нет «Состава») — тогда
  индекс активного зажимается в границы набора, панель не остаётся пустой.
- `[РАЗВИЛКА — решает Иван в браузере]` **тонкая полоса под табами** (как в окне
  агентов VS Code) или без неё. **Начинаем без полоски.** Мокап не собираем — Иван
  посмотрит глазами и решит.

### 13.8. Вложения на каждой форме

- Команда **«Загрузить»** (Codicon `new-file`) — в колонке команд шапки. Поля
  выбора файла в теле формы нет вовсе (принято 2026-07-26): системный диалог открывает
  сама команда, а в табе — только список.
- Строка вложения: **глиф** (§7a) · имя · описание · размер · дата загрузки · кто
  загрузил (человеческое имя, не логин) · команды-глифы `download` и `trash`.
- **Имя и «Скачать» — РАЗНЫЕ действия, дубля нет** (проверено глазами 2026-07-26):
  клик по имени **открывает** файл во вкладке браузера (смотреть), кнопка `download`
  **скачивает** (положить к себе). Оба нужны.
- Файлы — **отдельным табом** («Файлы»), содержимое — **обычный список** с такими же
  колонками, как везде.
- **Владельцы вложений** (решение Ивана 2026-07-26): изделие и 6 ордеров (уже есть)
  **+ проект** (договор, ТЗ), **закупка** (КП, счёт), **заказ** (счёт, скан накладной),
  **контрагент** («карточка предприятия» — docx/pdf с реквизитами; сейчас такой файл
  болтается по чатам, включая нашу собственную карточку — заведём себя контрагентом и
  положим файл туда).
- **Категория и Место — без файлов**, пока не заболит (добавить будет дёшево).

### 13.9. Один лэйаут на все формы

Канон применяется к **каждой** форме — зоопарк форм закрывается так же, как закрыт
зоопарк полей. Наследование вместо копипаста: правка вида — в одном файле.

**Что это отменяет:** `.subtitle`-описания под заголовком («Проект-исполнение · строки
добавляются в форме заказа») — по §12 они незаконны уже сейчас; разнобой кнопок в
`.kit-actions`; слитную ячейку `code`+`description` (антипринцип §7a).

**Правила, добытые раскаткой на все формы (Ф12c, 2026-07-26):**

- **Секция под формой — это таб, а не «ещё один список внизу»** (§13.7 в действии).
  Так переехали: панель закрытия проекта (стала табом «Склад»), pegging закупки
  (табы «Привязка» и «Заказы»), ре-материализация инвентаризации (таб «Списанные»),
  веер приходов заказа (таб «Поставки»).
- **Команда секции переезжает в колонку команд шапки** вместе с секцией: у формы
  один язык команд, своих кнопок у списков нет («Разрезать по проектам», «Закрыть
  проект» = обычная фиксация §5).
- **Общие поля шапки живут одним компонентом** (`OrderFields`: код · описание ·
  номер · дата · автор · проект-якорь), специфика вида добавляется после них.
  Пять копий одного `dl.props` разъезжались по подписям и ширинам.
- **Набор табов сужается там, где сущностей не бывает** (у покупного изделия нет
  «Состава», у внутреннего склада — «Приборов» и «Потребности»), но форма остаётся
  ОДНА: разных экранов для разных видов одной сущности не заводим (§13.10).
- **Органичное дополнение стека** (панель бюджета проекта) — слот `extra` между метой
  и табами: не список (табом быть не может) и не поле шапки.

### 13.10. Нет экранов без сущности

Следствие канона, принятое 2026-07-26 (идея Ивана про охват закупки). **Всё, на что
смотрят регулярно, — это сущность со своей формой.** Кастомных экранов, живущих мимо
канона, не заводим: у них нет `code`, нет фиксации, нет вложений, нет истории — и
именно они порождают зоопарк.

Диагностический признак кастомного экрана: он **прибит к сайдбару отдельным пунктом**
(не строкой списка) и рисует собственную вёрстку. На 2026-07-26 такой ровно один —
«Командный свод» (`extraTop` в режиме «Закупки», `CommandDeficitView` = третий скелет
формы после детальной и «＋ Новый»).

**Как лечится:** экран становится **проекцией обычной сущности**, а то, что он
показывал «по всему», выражается **полем охвата** этой сущности. Для свода это
множество проектов у Закупки (WAVE19 Ф13): все проекты отмечены = сегодняшний свод,
один = прозрачная закупка под один проект.

**Правило шире одного случая:** «общее» не выражается **отсутствием** связи. Ср.
решение по складу (README): «общего через `NULL` нет — его заменяют внутренние
проекты». Пустое поле означает «не задано», а не «все».
