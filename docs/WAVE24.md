**Отличия реализации от плана (по месту):**
- Перенос данных — RunPython **внутри `0006`**, а не отдельная management-команда: правило
  общее, без хардкода id, и едет на прод самим `migrate`. Проверен на снимке прода: у
  каждого заказа закупка, каждый одиночный заказ получил свою, «строка ⊆ план» везде.
- Остатки для окна «Новый заказ» берутся из проекции `allocation` (там уже есть
  `remaining`), отдельного эндпойнта `remainders` нет.
- «＋ Новый заказ — из закупки» в списке «Заказы» не рождает заказ, а переводит в режим
  «Закупки» — пользователь, привыкший к кнопке, не теряется.
- `DialogBox` получил слот содержимого и вариант `wide`; колонка галочек `.pick` стала
  общей ролью (`.grid`), была только у синхронизации с библиотекой.
- Таб «Закупки» в форме проекта (глиф режима `law`), мета проекта считает и закупки.
- **На снимке после миграции у одного проекта появились позиции «в плане»**: старая
  зафиксированная закупка хочет больше, чем взял её заказ. Это честное следствие новой
  арифметики, но на выкате стоит глянуть, не устаревший ли это план.

## Зачем

Пользователи бросили Закупку: холодный старт, сырость контура, срочность решений. Заказ
повзрослел и взял на себя планирование, а Закупка затихла как лишний шаг (на проде
закупок почти нет, часть — пустые обёртки вокруг заказа, новые заказы заводят без закупки).

Новая боль, которую Закупка решает органично: крупный заказ в переговорах разъехался на
несколько счетов и договоров разных контрагентов. Что-то оплачено,
что-то нет, и **нет механизма видеть, какие позиции уже под обязательством, а какие в
зоне риска**.

Старая боль, ради которой закупка была многопроектной (одинаковые заказы на разные
проекты), снята табом «Потребность» — многопроектность не нужна (все закупки на проде
однопроектные).

## Модель после волны

**Закупка = источник правды (что берём и сколько, для какого проекта). Заказ =
следствие работы с Закупкой, породившее обязательство.**

- `Procurement.project` — FK NOT NULL, PROTECT. Охват (`procurement_scope`) снят.
- `Purchase.procurement` — NOT NULL. `Purchase.project` — **снят** (выводится через
  закупку: property `Purchase.project` → `self.procurement.project`, в запросах
  `purchase__procurement__project`). Один источник правды о проекте.
- `ProcurementLine` — `UniqueConstraint(procurement, item)` (сейчас держит только движок).
- Инвариант **«строка заказа ⊆ план»**: изделие строки заказа обязано быть в строках его
  закупки. Держит движок (`add_purchase_line`; удаление строки плана, которую разбирают
  заказы, — отказ). CHECK через две таблицы не дотянется.
- **Фиксация Закупки** — инструмент работы с планом, а не блок для Заказа. Позиции
  зафиксированной закупки красят «Потребность» проекта 🟠. Черновая — не красит.
- **Фиксация Заказа = обязательство возникло** (оплачено или договор подписан) — нам
  остаётся ждать. Отдельного поля оплаты нет. Красит 🟢.

## Числа: колонка «Заказ» в «Потребности»

Новый член `planned` (в плане) у `ProjectSupply`, по проекту и Item:

```
planned = Σ по ЗАФИКСИРОВАННЫМ закупкам проекта:
          max(0, строка_плана.qty − Σ строк ЗАФИКСИРОВАННЫХ заказов этой закупки по Item)
on_order = (wip | purchased) + planned     # колонка «Заказ», от неё считается баланс
```

`purchased` — как сейчас (зафиксированные заказы − поступило). Пример: хотим 100, заказ
на 60 зафиксирован → purchased 60, planned 40, «Заказ» 100, баланс 0.

- **Ячейка «Заказ»:** глиф-ящик 🟠, если `planned > 0` (хоть часть держится только
  планом); 🟢, когда всё покрыто обязательствами. Расклад — в подсказке: «N в заказах ·
  M в плане». Движок отдаёт `planned` в строке, тон выбирает вью.
- **Баланс** — формула прежняя, `on_order` уже включает план. Тон колонки «Баланс» не
  меняется (0 — оранжевый «впритык»).
- **Ось «как дела» (`_supply_status`, цвет прибора/проекта):** не хватает → 🔴; держится
  на том, что зависит **от нас** (`planned > 0` или незакрытая комплектация `wip` у
  производимого) → 🟠; иначе 🟢 (на месте или по обязательству поставщика). Раньше
  оранжевым было любое «едет»; теперь зафиксированный заказ уже зеленит — «от нас всё
  сделано» (слова Ивана). *Решение по умолчанию — подтвердить на приёмке.*
- Остальные потребители `on_order` (`_coverage` в призраке комплектации,
  `project_plan_xlsx`, `_project_estimate`) получают сумму автоматически — проверить
  глазами, что смысл не поехал.

## Фазы

### Ф1. Схема + миграция данных (`0006`)

1. `Procurement.project` (nullable) → RunPython → NOT NULL.
2. RunPython (общий, без хардкода id; на проде прогнать по свежему снимку):
   - проект закупки = проект её заказов; **заказы разных проектов → `RuntimeError` с
     перечнем** (на снимке прода таких нет); закупка без заказов → `default_document_project`
     («Собственный склад») как фолбэк. Единственную такую на проде (черновик) Иван решил
     **удалить** — руками в UI ДО деплоя (черновик без заказов — удаление разрешено).
   - каждому заказу без закупки — **своя закупка**: тот же `code` (коллизия с кодом
     существующей закупки → суффикс « (заказ)»), `description`, `contractor`, `date`,
     `user`, `locked` = как у заказа; строки = строки заказа («хотим» = заказано).
   - каждой закупке — дописать недостающие строки плана из строк её заказов
     (qty = Σ по заказам): у пустых обёрток вокруг заказа строк плана нет вовсе, а
     инвариант «строка заказа ⊆ план» должен держаться с первого дня.
3. `Purchase.procurement` → NOT NULL; `Purchase.project` → снять; `ProcurementLine` →
   unique `(procurement, item)`.
4. README: обе диаграммы (продуктовая + техническая) в том же изменении —
   `PROJECT ||--o{ PROCUREMENT`, `PROCUREMENT ||--o{ PURCHASE`, у `PURCHASE` нет `project`.

### Ф2. Движок

- `Purchase.project` → property; все `purchase__project` / `project.purchases` /
  `pu.project` → через закупку (`set_receipt_purchase`, `create_receipt_from_purchase`,
  `project_supply`, `project_purchases`, `_purchase_rows`, проверка удаления проекта…).
- `ProjectSupply.planned(item)` + `on_order` = база + план; строка баланса несёт
  `planned`; `_supply_status` по правилу выше.
- `create_procurement(project, user, …)` — проект обязателен (рождение по «＋ Новый» —
  фолбэк `default_document_project`, как у ордеров Ф12e). `update_procurement(project=…)` —
  менять проект можно, **пока у закупки нет заказов**.
- **`create_purchase_from_procurement(procurement, user, item_ids)`** — черновой заказ:
  контрагент копией из закупки, строки по выбранным позициям с qty = **остаток**
  (`line.qty − Σ строк всех заказов закупки по Item`, не меньше 0). Пустой выбор законен —
  заказ «набить руками». Код — фолбэк «Заказ N». Работает и на черновой закупке.
- `procurement_remainders(procurement)` — остаток по строкам (кормит окно «Новый заказ»).
- `purchase_candidates(purchase)` — строки плана с остатком > 0, которых ещё нет в
  заказе (кормит выпадашку строки-призрака заказа; qty по умолчанию = остаток).
- `add_purchase_line` — отказ, если Item не в плане закупки. `remove_procurement_line` —
  отказ, если позицию разбирают заказы.
- `update_purchase` — без `project` и `procurement` (закупка задаётся при рождении и не
  меняется).
- Снять: `procurement_scope`, `purchase_demand`, `set_allocation`, `create_purchase`
  (рождение заказа «с нуля»). `procurement_demand` = `scope_demand([project],
  active_only=False)` + `_mark_taken`; деньги закупки — по `demand_map([project])`.
- `procurement_allocation` — проекция только для чтения: строка плана (баланс проекта
  теперь честный — проект один) → заказы (код, контрагент, замок, кол-во). `fan` — с
  контрагентом вместо проекта.
- Окно фиксации (`_consequences`): закупка — «позиции станут оранжевыми в „Потребности“
  проекта»; заказ — «обязательство возникло — позиции станут зелёными».
- Строки списков: у закупки появляется `project_code`.
- `seed_demo` — под новую модель.

### Ф3. API

- `POST /procurements/<pk>/purchases/` `{item_ids: [...]}` → форма нового заказа.
- `GET /procurements/<pk>/remainders/` (или в составе формы закупки — решить по месту).
- `GET /purchases/<pk>/candidates/`.
- `PATCH /procurements/<pk>` принимает `project_id`.
- Снять: `POST /purchases/` (рождение), `GET /purchases/<pk>/demand/`,
  `POST /procurements/<pk>/allocate/`; `PATCH /purchases/<pk>` без `project_id` /
  `procurement_id`.
- `GET /projects/<pk>/supply/` — добавить ленту закупок проекта.

### Ф4. Фронт

- **Закупка:** поле «Проект» (`ProjectField`, правится пока нет заказов) вместо охвата;
  кнопка **«Новый заказ»** → окно: список строк плана с остатком, галочки, «Выбрать все /
  Снять все»; по умолчанию отмечены строки с остатком > 0, строки с нулём видны, но
  сняты. Создать → открыть форму нового заказа.
- **Строки закупки:** одно поле ввода — «хочу» (кол-во плана). Аккордеон строки —
  распределение по заказам **только для чтения** (код заказа, контрагент, замок, кол-во).
  Колонка «Баланс» у строки плана теперь заполнена (проект один).
- **Заказ:** таб «Потребность» снят. «Проект» — ссылка только для чтения (выводится);
  «Закупка» — ссылка только для чтения. Строка-призрак — выпадашка **только из позиций
  закупки с остатком** (убывает по мере закрытия), qty преднабит остатком.
- **Список «Заказы»:** «＋ Новый» снят — заказ рождается только из закупки (пустая
  подсказка списка говорит, где его завести).
- **«Потребность» (`NeedTable`):** ящик колонки «Заказ» 🟠 при `planned > 0`, иначе 🟢;
  подсказка баланса — с «в плане N».
- **Проект:** таб «Закупки» рядом с «Заказы»/«Поставки».
- Веер «Заказы» в закупке: колонка «Контрагент» вместо «Проект».

- UI_GUIDE: правки там, где упомянуты охват / «Привязка» как поле ввода.
- JOURNAL — запись по итогам; карта журнала; BACKLOG — пункт «СЛЕДУЮЩАЯ СЕССИЯ»

### Ф6. Выкат

1. Иван: на проде удалить руками (UI) черновую закупку без заказов.
2. `deploy/pull_prod.sh --load` — свежий снимок; `migrate` локально; сверка: число
   закупок = старые − удалённые + одиночные заказы; у каждой закупки один проект; у
   каждого заказа закупка; строки заказов ⊆ строки плана; «Потребность» проекта до/после —
   баланс не изменился там, где закупки черновые (у зафиксированных он может сдвинуться
   только на план сверх заказов).
3. Иван: `deploy/deploy_local.sh` (секреты аргументами; preflight вшит).
4. Первая живая проверка — разнести разъехавшийся заказ по его счетам: расфиксировать,
   урезать строки под первый счёт, «Новый заказ» на остаток, проставить цены строк,
   зафиксировать оплаченные.
