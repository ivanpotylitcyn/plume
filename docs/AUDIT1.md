## А. Хорошее

Короткий список того, что прошло через весь проект стройно. Это не комплименты, а
**реестр инвариантов, которые надо беречь** при любых чистках.

1. **Один писатель склада.** `engine.rebuild_movements` — единственная точка записи
   `StockMovement`; гейт Ф15 («замок гейтит склад») врезан ровно в неё, поэтому
   остатки/дефицит/бюджет/карта подчиняются правилу автоматически. Админка честно
   read-only по движковому (`_ReadOnlyAdmin`), с внятным объяснением границы в
   docstring [admin.py](../backend/plume/admin.py).
2. **Двухслойные инварианты.** Каждое правило живёт дважды: CHECK в БД (страховка от
   прямого ORM/админки) + прикладной гейт с дружелюбной ошибкой
   (`purchase_locked_has_contractor` + `lock_purchase`; `item_locked_has_category` +
   `lock_item`; `_require_header`). Урок Ф12e («CHECK без гейта — это 500 в лицо»)
   выучен системно.
3. **Одна таблица ордера + proxy-виды.** `StockDocument` + `_KindManager` — снос MTI
   пережили 108 обращений `Receipt.objects…` без правки. Единая дорога рождения
   (`_born_order` + `fallback_code` + `require_unique_code`), единая правка шапки
   (`update_document` + `_UNSET`-часовые), единое удаление (`delete_stock_document`).
4. **Единая ось `locked` на пяти сущностях** — одно поле, один глагол, одни
   эндпойнты `lock/unlock`; сильная у документов (арифметика), слабая у справочников
   (заморозка). Ни одного второго словаря статуса не осталось.
5. **`code`+`description` везде** — включая фолбэк «{Вид} {id}», мягкую уникальность
   и пустой титул как «подталкивание». Ноль исключений в живом коде.
6. **Шов движок↔вью выдержан.** Движок отдаёт смысл (`contractor_mismatch`,
   `counterparty_sides`, `project_health`, `supply/shipment = интеграл или None`),
   вью выбирает знак. Тема: `models.THEMES` (слаги) → `engine.set_theme` (страж) →
   `core/theme.ts` (применение) → `themes/*.css` (значения) → `registry.ts` (ярлыки) —
   образцовая слоистость, ни одна сторона не знает лишнего.
7. **Один лэйаут форм.** `FormShell` + `OrderFields` + `useOrderForm` +
   `Field/TextField` + единый `Dropdown`/`Picker`/`AnchoredMenu` (порталы) — шесть
   видов ордера сведены к диспетчеру на 55 строк ([OrderForm.tsx](../frontend/src/OrderForm.tsx)).
   «Неполированные» вью (Transfer/Location/Writeoff/Requisition/Inventory/Relocation)
   на деле **уже на каноне** — отстаёт только тело комплектации (см. Б1б-1).
8. **CSS-иерархия по заветам:** структура в `index.css` токенами, значения в темах,
   приглушение — инверсией умолчания (`table.grid td` + роли `.c-key/.num/.code`),
   171 использование `var(--…)`. Новая тема = один файл + строка реестра — проверено
   светлой темой.
9. **ER-диаграммы README = models.py буквально.** Сверено поле-в-поле, включая
   nullable-нотацию `|o` и порядок полей. Расхождений ноль. Правило «диаграммы —
   источник правды» работает.
10. **Гигиена деплоя.** `preflight.sh` (секреты/миграции/тесты/сборка) вшит в
    `deploy_local.sh`; секреты — аргументами; греп по хостам/адресам/ключам чистый;
    `.env` и `deploy/snapshots/` в `.gitignore` (проверено `check-ignore`).
11. **Тесты названы поведением** (Ф16), докстринги переписаны, покрытие сверялось
    при чистке. Сюита реально ловит регрессии (поймала `origin__receipt__purchase`).
12. **Комментарии-журнал в коде.** `models.py`/`engine.py` читаются как документация
    решений с «почему». Это осознанная ставка проекта; её цена — устаревание
    (см. Б1а-6, Б2а-4) — но баланс сейчас сильно в плюс.

## Б1а. Баги и костыли — править легко (1–2 сессии)

1. **500 на создании закупки с занятым кодом.** [views.py:1779-1785](../backend/plume/views.py#L1779-L1785) —
   единственный POST-создатель без `try/except ValidationError`:
   `engine.create_procurement` зовёт `require_unique_code`, и занятый `code` в теле
   запроса уронит вьюху в 500 (Django-ValidationError DRF не конвертирует). Все
   остальные create-вьюхи обёрнуты. Из UI не воспроизводится («＋ Новая» шлёт пустое
   тело), но это дырка в едином паттерне. *Фикс: обернуть как соседей.*
2. **`StockMovement.Type.RETURN` — мёртвый enum.** [models.py:815-818](../backend/plume/models.py#L815-L818).
   `rebuild_movements` пишет только RECEIPT/ISSUE; RETURN не создаётся нигде
   (греп по движку — ноль вхождений). При этом README обещает «компенсирующий
   `RETURN`» (см. Б3-3). *Решить: снести значение (миграции не надо — это choices)
   или узаконить сценарий. Решение — до сквоша.*
3. **`BomLine.position` — приговорённое поле живёт.** FIELD_MATRIX (A1) и JOURNAL
   2026-07-05: «мёртвое поле → удалить из схемы перед релизом». Факт: поле в схеме
   ([models.py:377](../backend/plume/models.py#L377)), в движке (`add_bom_line`),
   в API (`api.ts:663-665`) — а форма изделия его **не показывает** (греп по
   ItemView — ноль). *Решить судьбу до сквоша миграций: снести или вывести на форму
   (позиционное обозначение — вообще-то полезная вещь для плат).* 
4. **Черновое списание уже предлагает ре-материализацию.**
   [engine.py:3812-3835](../backend/plume/engine.py#L3812-L3835) `written_off_lots`
   суммирует строки списаний **без фильтра `document__locked`** — лот из чернового
   акта уже виден в пикере инвентаризации как «списанный, можно вернуть». Расходится
   с границей Ф15 («черновик — намерение, не факт»), которую держат все соседние
   интегралы (`_counterparty_supply`, `_project_spent`, `_line_received`).
   *Фикс: `+ document__locked=True` в оба фильтра.*
5. **Даблклик в панели закрытия плодит второй акт.** [engine.py:2323-2361](../backend/plume/engine.py#L2323-L2361)
   `writeoff_lot`/`requisition_lot`: если лот уже лежит в черновом акте, повторный
   клик **создаёт новый акт** с тем же остатком — после фиксации обоих лот уйдёт в
   минус. Панель показывает `closing_drafts`, но от повторного клика не защищает
   (после Ф15 остаток на панели не гаснет до фиксации — клик «не сработал» выглядит
   правдоподобно). *Фикс: лот уже в черновом закрывающем акте → дружелюбный отказ
   («остаток уже в акте X — зафиксируйте его»), а не новый документ.*
6. **Докстринг `library_diff` врёт про замок.** [engine.py:4135-4143](../backend/plume/engine.py#L4135-L4143)

7. **Два живых предупреждения oxlint.**

## Б5. Зрелость сквозных решений (описание — схема — движок — вью)

Общая оценка: **взрослая**. Ось выдержана: правило рождается решением (JOURNAL),
ложится инвариантом в схему, гейтом в движок, знаком во вью — примеры Ф15/Ф17/Ф3
проходят все четыре слоя без потерь. Найденные «детские места» — не мины, а
осознанные упрощения, которым пора завести наблюдение:

1. **Транзакционность** — см. Б1а-8 (`ATOMIC_REQUESTS`). Единственное место, где
   упрощение может молча испортить данные.
2. **Конкуренция двух операторов.** Прод многопользовательский, а версий/оптимистичных
   блокировок нет: два человека в одной форме перетирают друг друга по last-write-wins,
   и автосейв это ускоряет. Для команды в несколько человек — приемлемо; знать и не
   удивляться. Дешёвая полумера, если заболит: сверка `locked`-состояния в PATCH.
3. **N+1 по философии.** `/api/items/` = `item_is_used` (6 Exists) × N изделий;
   `/api/projects/` = полное разузлование `project_health` × N проектов; список
   заказов = `purchase_coverage` × строки. «Данных мало, всё свежее» — честная
   ставка MVP, но это те три точки, где рост данных проявится первым. Действие
   сейчас: замерить на снимке прода (`pull_prod`), записать базовую цифру; чинится
   точечно (annotate/prefetch), волны не потребует.
4. **Права.** Один уровень доверия («любой залогиненный — полноправный оператор»),
   `attachment_download` отдаёт файл любому залогиненному. Для внутреннего
   инструмента — осознанно и записано в settings; не долг.
5. **Фронт без тестов (0).** Держится на tsc + тонкости вью-слоя (логика в движке).
   Это правильный баланс; единственное место, где логика утекла во вью, — сборка
   `orderEntries`/фильтров в App.tsx, и она тривиальна. Не заводить тесты ради
   тестов; следить, чтобы вью не умнела.
6. **Джанго-миграции: хвост из 17.** Сквош в `0001_initial` перед 1.0 — уже принятая
   политика; аудит добавляет только порядок: сначала решения Б1а-2/Б1а-3 (RETURN,
   position), потом сквош, потом архивация docs (В-1).
