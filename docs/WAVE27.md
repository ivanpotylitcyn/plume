## Зачем

Складской контур не запускался, потому что лоты негде увидеть: `Lot` — главная учётная
единица, но ни списка, ни формы у него нет. Лоты двух прод-поставок видны только в табе
проекта. Оффлайн-практика добавляет второй довод: УПД оформляет бухгалтерия, а взять
компоненты в работу можно только по **Требованию** — официальному документу, который
потом вписывают в акт комплектации.

## Язык (глоссарий после волны)

| Термин | Что это | Код |
|---|---|---|
| **Склад** | режим: список лотов (что физически лежит) | mode `stock`, глиф `layers` |
| **Локация** | место хранения; прежний режим «Склады» | `Location`, mode `locations`, глиф `location` |
| **Центральный склад** | синглтон-локация: сюда приходят поставки; в норме **пуст** | `Location.central` |
| **Требование** | НОВЫЙ официальный вид: Центральный → наша локация, один проект | kind `requisition` (новый смысл) |
| **Перемещение** | онлайн-ход между НАШИМИ локациями, юридической силы нет | kind `relocation` (как было) |
| **Перевод** | прежнее «Требование/отпочкование»: часть лота → в другой проект новым лотом-потомком | kind `reassignment` (переименование) |

**Лот на Центральном = задача «оформить Требование»** (очередь, а не покой).

## Ф1 — Центральный склад и локация «Куда» (схема + движок)

- [x] `Location.central` — синглтон: не удаляется, переименовывается. Мёртвое текстовое
      `kind` снять. **Решить на старте:** синглтон в БД через `BooleanField(null=True,
      unique=True)` (True / NULL — MySQL пускает много NULL под unique) или прикладной
      гейт, как у внутренних проектов. Рекомендация — БД (инвариант там, где он дешёв).
- [x] `_main_location()` (код `MAIN` или первый id) → `central_location()` по флагу.
- [x] `StockDocument.location` («Куда», FK nullable) — у **рождающих** видов: поставка,
      комплектация, инвентаризация, требование. CHECK применимости по `kind` + CHECK
      «зафиксирован ⇒ задан» (канон Ф14). Дефолт рождения: поставка — Центральный;
      комплектация и инвентаризация — **не Центральный** (гейт движка + `clean()`: CHECK
      не видит чужую таблицу).
- [x] `rebuild_movements`: место рождения = `origin.location`; у Перевода — место парной
      строки источника (потомок рождается там, где лежал источник: проект меняется, место нет).
- [x] **Выбор лота = выбор места** для строк расхода (комплектация, передача, списание,
      перевод): пикер отдаёт пары «лот @ локация, остаток», строка хранит локацию пары.
      Снять дефолты `location or _main_location()` и хардкод передачи (`engine.py` ~3026 —
      сейчас списывает всегда с главной).
- [x] Перемещение не касается Центрального ни одной стороной (гейт движка).
- [x] Миграция `0012` (`0011` — переименования Ф0): завести «Центральный склад» (`central`), поставкам проставить его в
      `location` (прод: 2 поставки — их лоты встают в очередь «ждут Требования»; пять
      существующих локаций остаются нашими); dev-комплектациям/инвентаризациям — прежнюю
      главную; `rebuild_all`. Прогон на свежем снимке прода до выката.
- [x] Обе диаграммы README, тесты (место рождения по видам, пары пикера, синглтон, гейты),
      журнал.

## Ф2 — Требование (новый вид)

- [x] `DocumentKind.REQUISITION` = «Требование» (новый смысл), proxy `Requisition`.
      Механика перемещения (пара `−q`@Центральный / `+q`@«Куда»), источник — **всегда**
      Центральный, «Куда» — шапка (`StockDocument.location`). Один проект (`doc.project`),
      пикер — лоты проекта на Центральном. Шапка строгая: `date` + `number`.
- [x] Движок: пару ходов перемещения обобщить на оба вида (не копировать).
- [x] Фронт: форма Требования (из `RelocationView`), вид в «Ордерах», блок «Деньги» —
      «выдали на сумму» (у Перевода остаётся «перевели», канон в26).
- [x] **Требование в акте комплектации — выводится, связи в схеме нет:** по списанным лотам
      — зафиксированные Требования проекта, которые их привезли. Лот может прийти несколькими
      Требованиями (катушку берут частями) — акт собирает все. Не было Требования (паяли с
      Центрального) → пусто, и это видно. В форме комплектации — список; печатная форма акта —
      в Ф5 вместе с долгом сценария.

## Ф3 — Режим «Склад» и форма лота

- [x] Движок `stock_lots()`: живые лоты (остаток ≠ 0; минус виден как аномалия) + режим
      «исчерпанные»; лоты черновиков не показываем (на складе их нет, Ф15). Строка: код (PN;
      пуст → наименование), наименование, `native`, категория, проект, остаток, «на Центральном».
- [x] Фронт: режим `stock` (`layers`) **над** «Локациями». Фильтры: категория (**обе
      стороны** справочника — на складе всё вместе), локация, проект (как в «Заказах»),
      переключатель «исчерпанные».
- [x] Движок `lot_form(lot)` и форма лота — **целиком read-only** (идентичность правится в
      origin-ордере: Поставка / Комплектация / Инвентаризация):
  - **Шапка** (без локаций): глиф, код (PN), наименование; якоря-ссылки — изделие, проект,
    origin-ордер, предшественник.
  - **Деньги** — раскладка жизни: рождено (шт · ₽ · цена штуки) = впаяно + передано +
    списано + переведено + остаток; у строки «Остаток» — разбивка по локациям. Сумма
    сходится до копейки (явная сверка + тест — принцип «одинаковые числа совпадают», 10-19).
  - **Табы:** «История» (`notebook`: рождение, Требования, Перемещения, Переводы, расходы —
    дата, ордер, локация, ±шт, ±₽) · «Применение» (`rocket`: комплектация → лот-прибор →
    сколько впаяно) · «Состав» (`chip`, только у лота-прибора: паспорт — лоты компонентов
    его комплектации, рекурсивно по подсборкам).
- [x] Адрес `/lot/ID`, `EntityLink kind="lot"`: **все упоминания лота становятся ссылками**
      (строки поставки/комплектации/передачи/списания/перевода/перемещения/требования, таб
      склада проекта и изделия, локация). Палитра команд.
- [x] «Локации»: заголовок и глиф `location`, форма — код, описание, Деньги (★ «лежит на
      сумму», в26), табы «Склад» (строки лотов → форма лота) и «Ордера» (Требования и
      Перемещения с её участием). У Центрального корзины нет.

## Решено на проходе (автономно, рекомендации Claude — проверить на приёмке)

1. **Синглтон Центрального — в БД:** `central = BooleanField(null=True, unique=True)` +
   CHECK «True или NULL». Миграция заводит Центральный только в БД с данными; в пустой
   (тесты, первый сид) его лениво создаёт `engine.central_location()`.
2. **Миграция `0012` на проде:** заводит «Центральный склад» (код `Центральный`),
   ставит его в «Куда» обеих поставок и переносит туда всё, что лоты поставок делали на
   прежней главной (`103 ЛК`), — строки и проекцию. Прогнано на снимке
   `prod-20261021-1058`: остатки и суммы совпали (4 шт / 20 054,26 ₽ и 20 шт /
   19 907,23 ₽), `rebuild_all` ничего не сдвинул. Пять локаций остались нашими.
3. **«Куда» по умолчанию** у комплектации / инвентаризации / требования — первая
   нецентральная локация по id (на проде это `103 ЛК`). Меняется в шапке.
4. **Место строки без пары** (старые пути API, тесты): лот лежит в одном месте — там; в
   нескольких — отказ «выберите, откуда»; нигде (минус) — место рождения.
5. **Ключи API** партии — `lot_code` / `lot_description` (в строках рядом `item_code`,
   голые `code`/`description` путались бы); поля модели — `code` / `description`.
6. **Требования в акте** — поле шапки комплектации «Требования» (только чтение, ссылки);
   печатная форма акта — вместе со сценарием комплектации.
7. **Требование:** ★ «Деньги» — «выдали на сумму»; пикер — лоты проекта на Центральном,
   кол-во по умолчанию — всё, что там лежит.
8. **Список «Склад»:** фильтр наличия «на складе / исчерпанные / все»; справа — остаток;
   код строки = PN, пусто → наименование. **«Локации»:** Центральный первым с подписью.
9. **Перемещение:** Центральный не предлагается ни в «откуда», ни в «куда»; пикер
   перемещения не видит лоты, лежащие только на Центральном.
10. **Демо-сид** переведён на контур: поставки → Центральный, ТР-1/ТР-2, сборка на 105.
